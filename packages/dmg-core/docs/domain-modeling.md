# Моделирование домена

**Назначение:** куда помещать доменную логику, как модули делят знание, как ошибки и данные пересекают границу модуля.

---

## 1. Модуль-владелец

1. **Определи владельца.** Чьи данные нужны правилу — там и живёт логика.
2. **Выбери объект** — ближе к данным, которыми оперирует правило. Policy или доменное правило — решает вопрос «зависит ли ответ от того, кто спрашивает» (D-40):

| Логика | Объект |
|---|---|
| Инвариант, переход, вопрос в пределах одного агрегата | Ar |
| Право **субъекта** на действие (роль, владение, контекст — сколько угодно агрегатов) | Policy |
| Допустимость действия при текущих состояниях агрегатов, **без субъекта** (уникальность, допуск) | доменное правило (D-40) |
| Мутация нескольких агрегатов, композиция правил с операциями | DCS |
| Вычисление на чтение поверх нескольких агрегатов | DQS |
| Нужны данные/решение другого модуля | делегирование в его Ar/Policy/DQS (по `dependsOn`) |

3. **Делегируй минимумом.** Зависимый модуль передаёт владельцу только нужное (идентификаторы, примитивы, его же агрегаты).
4. **Не дублируй.** Если модуль-владелец уже отвечает на вопрос (активен ли пользователь) — зависимый модуль не пишет то же правило у себя.
5. **Называй доменно.** Метод отвечает на доменный вопрос (`isAssignedTo`, `isActive`), а не описывает структуру данных (`hasAssignment`, сравнение `status === 'done'` снаружи Ar).

## 2. Антипаттерны

- ❌ Доменное решение в UC, ER, Job, Story (if по статусам, вычисления, выбор текста по состоянию).
- ❌ Чтение полей entity вне Ar и рендереров (форма state в Def контрактов — можно, D-39).
- ❌ Правило без субъекта в Policy (уникальность, допуск) — это доменное правило (D-40).
- ❌ Policy, которая разбирает структуру данных чужого модуля.
- ❌ `process.env` / глобальный `config` в домене и UI-компонентах — данные окружения через резолвер приложения.
- ❌ Маскировка рассогласования данных пустым массивом или `undefined` — это баг, `throw`.
- ❌ Скрытые межмодульные мутации из UC (снять роль, уведомить) — по умолчанию это событие и ER в модуле-владельце. Мутация не скрыта, если Def вызываемого UC объявлен в `calls` (D-42, D-43), а место вызова выбрал владелец проекта — по каждому случаю ([use-case.md](./guides/use-case.md) §1).

## 3. Кейс: назначение задачи исполнителю

*Задача (учебный модуль `todo`):* назначить задачу можно только активному пользователю модуля `users`; назначать может владелец задачи или администратор.

- ❌ *Всё в `TaskPolicy`:* Policy спрашивает `users` и разбирает его ответ — знание чужого модуля утекло в право субъекта.
- ❌ *Проверка в UC:* `if (!user.active) return err(...)` в `execute` — доменное решение в прикладном слое (API-01).
- ❌ *Активность исполнителя — в Policy:* ответ не зависит от того, кто назначает, — это не право, а доменное правило (D-40).
- ✅ *Итог:* Policy `todo` отвечает только «может ли этот субъект назначать» (`canManage`: владелец или администратор). UC `assignTask` в `load` спрашивает `users` (`this.call(GetUserUcDef, …)`, Def — в `calls`) и кладёт ответ в контекст; доменное правило `assigneeActive` решает о допуске и при отказе возвращает ошибку `todo` (`TASK_ASSIGNEE_INACTIVE`); `USER_NOT_FOUND` пробрасывается по ссылке. Образец — [assign-task.uc.ts](../src/testing/example/todo/task/uc/assign-task.uc.ts), [task.rules.ts](../src/testing/example/todo/task/task.rules.ts).

## 4. Границы модулей

**Данные.** Другой модуль получает агрегаты через фасад как `ReadonlyAr` и пользуется их API (`TaskAr.readonly(res.value).isAssignedTo(userId)`). Мутировать чужой агрегат нельзя — только его UC/фасадом владельца.

**Связь.** Вызывающий UC/ER/Job объявляет в `calls` Def UC модуля-владельца (с `'system'` в `callers`) и вызывает их `this.call(def, …)` через фасад владельца (D-42, D-43); граф и проверки видят связь «UC → UC».

**Ошибки.** Фасад возвращает `Result` с ошибками вызываемого UC (его `errors`). Вызывающий UC может:
- **пробросить** ошибку зависимости — сослаться на неё в своём `errors` (без переименования; коды уникальны в приложении);
- **перевести** в свою — только если смысл меняется. Пример: неактивный пользователь при назначении → `TASK_ASSIGNEE_INACTIVE` в `todo`.

Пробросить можно только то, что объявлено в `errors` вызываемого UC. Исход «сущности нет» (`USER_NOT_FOUND`) — штатный: он объявляется в UC владельца, и зависимый модуль пробрасывает его как есть, а не подменяет своей ошибкой.

**Поведение.** Нижестоящий модуль не вызывает вышестоящий. Нужна реакция «наверху» — публикуется событие, вышестоящий подписывается ER.

## 5. Агрегат

- Создание и восстановление разделены: `Ar.create(input, at): Result<Ar>` (бизнес, событие; базовые поля — `Aggregate.newState(uuid, at)`) и `Ar.restore(snapshot)` (доверенно, без событий).
- Время — аргумент операции (`complete(at)`), часы домен не читает (D-34). Статус меняется только через `transition` по правилам Def (D-35); версию ведёт база (D-36).
- Мутация: проверка → черновик → валидация инвариантов → фиксация. Повреждённое состояние в памяти невозможно.
- Вопросы к состоянию — методами, а не геттером на каждое поле; идентификаторы (`uuid`, связи) — геттерами. Данные для контракта ошибки или выхода отдаёт метод Ar, строящий этот контракт (Ar строит ошибку своей группы с нужным payload), а не геттер на поле (D-39).
- VO не имеют `createdAt`/`updatedAt` и идентичности.

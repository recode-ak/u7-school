# Ошибки и Result

**Назначение:** как домен и прикладной слой сообщают об отказах. `Result` (`ok`/`err`), `defineErrors`, `CoreErrors` и UoW — в `dmg-core`. Маппинг ошибок на транспорт — [transport.md](./transport.md).

---

## 1. Ключевые правила

1. Штатный бизнес-отказ («задача уже выполнена», «нет прав», «не найдена») — **значение** `Err`, а не исключение.
2. `throw` допустим только для: бага, нарушения инварианта (данные повреждены), системного сбоя (диск, сеть).
3. Мутирующие методы Ar, DCS, фасады и UC возвращают `Result<T, E>`; `E` — union объявленных ошибок. Методы-вопросы и DQS `Result` не возвращают.
4. UC может вернуть **только** ошибки из своего `errors` плюс базовые ядра — проверяет компилятор.
5. Вызывающий код (story, ER, UC) обрабатывает `Err` явно: `switch` по `code` с веткой по умолчанию.
6. Нарушение, которое в production не должно ронять операцию пользователя (расхождение реализации с контрактом, подозрительное, но не опасное состояние), не бросается и не проглатывается молча: в test и development — исключение, в production — как минимум `logger.warn` с источником (ERR-07). Пример — сверка `emits`/`touches`/`calls` в UoW и резолвере.

## 2. Модель ошибки

`code` + `kind` + `label` + `description` + `payload`. **Ошибка не знает транспорт.**

| kind | Смысл | Примеры |
|---|---|---|
| `validation` | вход не прошёл схему | `INPUT_VALIDATION` |
| `unauthorized` | `kind` вызывающего не входит в `callers` UC | `UNAUTHORIZED` |
| `access` | политика отказала (+ правило и `denyMessage`) | `ACCESS_DENIED` |
| `not_found` | сущности нет | `TASK_NOT_FOUND` |
| `conflict` | состояние не допускает операцию | `TASK_ALREADY_DONE` |
| `internal` | сбой, баг, невалидный выход | `SERVER_INTERNAL`, `OUTPUT_VALIDATION` |

`kind` нужен для общей обработки: ветка по умолчанию в UI, уровень логирования, алерт на `internal`, маппинг в адаптерах.

- Коды — UPPER_SNAKE с префиксом сущности, **уникальны в приложении** (контрактный тест).
- Агрегат объявляет ошибки группой `defineErrors`; UC и фасад **ссылаются** на них, результат Ar возвращается как есть.
- Ошибки зависимостей — по ссылке через контракт фасада; перевод — только при смене смысла (см. [domain-modeling.md](./domain-modeling.md) §4).
- Базовые (`UNAUTHORIZED`, `INPUT_VALIDATION`, `ACCESS_DENIED`, `OUTPUT_VALIDATION`, `VERSION_CONFLICT`, `SERVER_INTERNAL`) подмешивает ядро.

## 3. Исполнение UC (`handle`)

Право вызова (`callers`) → валидация входа → `load` → Policy → доменные правила (`rules`) → `execute` → валидация выхода → при `Ok`: `uow.commit()` → публикация событий зарегистрированных агрегатов (с проверкой `emits`) → запись в лог операций (и при отказе, D-43). Шаги — `protected` методы `UseCaseFromDef`.

- **Порядок проверок прав.** Первым проверяется право вызова по виду вызывающего (`callers`), до чтения данных. Policy контекстна (владелец, участник), поэтому идёт после `load`: отказ «не найдено» возможен раньше `ACCESS_DENIED`. Это допустимо — идентификаторы UUID не перебираются; если существование записи само секретно, Policy-правило без контекста выносится в отдельную проверку до `load`.
- **Выход проверяется до фиксации.** Невалидный выход — баг реализации (`OUTPUT_VALIDATION`, `internal`): операция отказывает целиком, ничего не сохраняется и не публикуется, клиент может безопасно повторить. Частичный или непроверенный ответ не отдаётся — он ломает клиента и может раскрыть лишние поля.

- Непредвиденное исключение ловится, логируется и превращается в `SERVER_INTERNAL` — процесс не падает.
- События публикуются **только у записанных агрегатов**: при успешной фиксации — все; при сбое записи N-го агрегата (`VERSION_CONFLICT` или исключение) записанные до него не откатываются (D-15) и их события публикуются, события N-го и следующих — нет.
- **Параллельные изменения** (D-36): репозиторий сверяет версию агрегата (`assertVersion`) и бросает `VersionConflict`; UoW возвращает `VERSION_CONFLICT` (`conflict`) — клиент повторяет операцию с актуальными данными. Новый агрегат при занятом uuid — тоже конфликт.
- UoW на файловом хранилище сохраняет последовательно, без отката (D-15). Пока он есть, UC по возможности меняет один агрегат; согласованность между модулями — через события.
- ER возвращает `Result`; сбой реакции логируется и попадает в журнал сбоев, а не гасится.

## 4. Тестирование

- Проверяется конкретный `code` (и при необходимости `kind`), а не просто факт ошибки.
- Ar: тест на каждую ветку `Ok`/`Err` каждого мутирующего метода.
- UC: тест на каждую собственную объявленную ошибку.
- Хелперы `expectErr`/`expectOk` — [testing.md](./testing.md) §2.
- Ядро: тесты `handle()` на перехват исключений, порядок commit → publish, валидацию выхода до фиксации.

# Aggregate — гайд

**Назначение:** Def агрегата (`<A>ArDef`: статусы, переходы, отказы) и класс Ar, который отвечает за правила и мутации одного агрегата: `<domain>/<m>/<a>/<a>.ar.ts`.

---

## 1. Когда применять

- У сущности есть жизненный цикл (статусы и переходы) или инварианты, которые нужно держать в одном месте.
- Решение принимается по данным одного агрегата. Если нужно несколько агрегатов, это DCS (DOM-06, [repo.md](./repo.md)); если вопрос «можно ли» зависит от субъекта — Policy (DOM-05, [policy.md](./policy.md)).
- Структура полей описана в state ([state.md](./state.md)), Ar её не дублирует.

## 2. Команда

`dmg-core gen aggregate <m>.<a> --write` создаёт state, events, errors, Ar, Policy и repo. Заполни TODO в Def (`statuses`, `transitions` с `from`/`to`/`rejects`) и методы Ar. Генератору нужен паспорт `<m>.module.ts`.

## 3. Образец

- [task.ar.ts](../../src/testing/example/todo/task/task.ar.ts): `TaskArDef` (3 статуса, 2 перехода, `rejects` для каждого статуса вне `from`); `TaskAr` — `create`/`restore`, переходы `complete`/`archive` через `this.transition`, мутации без смены статуса `assign`/`unassign` через `this.change`; отказы метода — `RejectOf<…, 'complete'>`, а не вся группа.
- [task.ar.test.ts](../../src/testing/example/todo/task/task.ar.test.ts): `create`, round trip `snapshot`, запись не по схеме — исключение, успех и каждый отказ перехода, повтор без изменений, методы-вопросы.
- [user.ar.ts](../../src/testing/example/users/user/user.ar.ts) и [тест](../../src/testing/example/users/user/user.ar.test.ts): минимальный агрегат — один переход `remove` и метод-вопрос `isActive`.
- [task.errors.ts](../../src/testing/example/todo/task/task.errors.ts) и [task.events.ts](../../src/testing/example/todo/task/task.events.ts): группы, на которые ссылаются `rejects` и `emit`.

## 4. Чеклист правил

- DOM-02 — переходы и `create` возвращают `Result`, методы-вопросы (`isOpen`, `isAssignedTo`) — `boolean`.
- DOM-03 — `create` (новый агрегат) и `restore` (из хранилища) разделены, Ar не создаёт другой Ar.
- DOM-04 — наружу идут идентификаторы и методы-вопросы, геттеров на каждое поле нет.
- DOM-14 — `uuid` и момент `at` приходят аргументами, статус меняет только `transition`.
- MAN-12 — у каждого перехода `rejects` покрывает все статусы вне `from` ошибками своей группы.
- MAN-01 — у Def есть `label` и `description`, у статусов — `label`.
- ERR-01 — штатный отказ возвращается как `Err` и не бросается.
- CODE-02 — `private`, а не `#private`.

## 5. Типичные ловушки

- **Фабрика на каждую ветку, хотя ветку выбирает внешний контекст.** Если начальный статус решают данные вне агрегата (их видит только UC), фабрика одна, а вход `create` несёт выбранный вариант. Отдельные фабрики оправданы, когда ветки различаются входом или инвариантами самого Ar.
- **Свой список статусов в предикатах.** Предикат «можно ли перейти» дублирует `from` Def и расходится с ним; нужен вопрос — назови его по смыслу (`isOpen`), а допустимость перехода оставь `transition`. Условие сверх статуса живёт в одном приватном методе, который зовут и предикат, и операция.
- **Проверка статуса, которую уже делает Def.** В методе с `transition` статус не проверяй — база вернёт отказ из `rejects` (D-35). Своя проверка уместна только в `change`, где перехода нет (`assign` — только открытой задаче).
- **Повтор как ошибка.** Тот же исполнитель или снятие без назначения — `ok` без изменений: повтор ничего не пишет, ER остаётся идемпотентной без сравнения статусов.
- **`crypto.randomUUID()` и `Date.now()` в Ar.** В домене часов нет: `uuid` и `at` берёт прикладной слой (DOM-14, ARC-03).
- **`snapshot()` вне репозитория.** Снимок — только для записи (DOM-17). Состояние наружу (выход query, рендерер UI) — `view()`: по умолчанию это `snapshot()`, агрегат переопределяет его, объявив форму вторым параметром `Aggregate<D, V>` (D-44). Объявил `V` — переопредели `view()` и собери объект явно (`{ uuid: this.uuid, … }`), не `{ ...this.state }`: тип `V` не убирает лишние поля. Данные для контракта ошибки или выхода, которые не являются состоянием, — метод Ar (D-39).

## 6. Как тестировать

На каждый переход — тест успеха (статус `to`, `updatedAt = at`, `version + 1`, событие) и тест каждого отказа из `rejects` по `code` (TST-01). Для `create` — каждая ветка, для `restore` — round trip `snapshot` и запись не по схеме. Мутации без перехода — версия растёт, статус прежний; повтор — без изменений и событий. Описания и `rejects` проверяет `checkDefs` по паспорту модуля. Тесты — 10–20 строк ([testing.md](../testing.md), TST-04).

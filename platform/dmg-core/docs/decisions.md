# Решения (ADR-список)

**Назначение:** реестр архитектурных решений платформы DMG. Новое решение добавляется строкой `D-NN`, старое помечается «заменено D-NN». Номера сквозные с проектом-источником, поэтому пропуски допустимы: решения проекта (процесс, документация, переход) в пакет не входят.

---

## Основа

**D-01. Манифест — единый источник истины.** Каждая доменная сущность объявляется один раз декларативным объектом (`*Def`). Из него выводятся типы, схемы, свойства базовых классов, транспорт, документация, MCP и контрактные тесты. *Почему:* сейчас одна команда описывается в 5–6 местах, связи скрыты в коде.

**D-02. Четыре оси.** Платформа (`dmg-core`, пакет приложения) → домен (пакет домена) → прикладной слой (прикладной пакет модуля, строго 1:1 с модулем домена) → входные адаптеры (UI и транспорты). См. [layers.md](./layers.md).

**D-03. Домен един, чист и синхронен.** Пакет домена содержит всю предметку и все контракты (UC, ER, Job, фасады, модули). Никакого IO; асинхронность — только `Loader<T>`. Любой слой пользуется доменом через его API, но только в рамках `dependsOn` модулей (граф модулей — DAG).

**D-04. Пакет приложения — платформа приложения.** Замыкает дженерики (пользователь, резолверы, сборка модулей), импортирует домен. Доменных сущностей не содержит: пользователь и роли — модуль домена.

## Доменный API

**D-05. Entity видят только Ar и конечные рендереры.** Все остальные (UC, ER, Job, Story, DCS, DQS, Policy, фасады, репозитории) работают только через API доменных объектов. Рендереры UI (компоненты отображения) могут работать с entity напрямую, в т.ч. для реактивности. Репозиторий работает через `Ar.restore()` / `ar.snapshot()`. Форма state в контрактах и показ полей — уточнено D-39.

**D-06. Уровни доменного API: Ar → Policy → DCS / DQS.** `DomainCommandService` (DCS) координирует несколько агрегатов с мутацией и возвращает `Result`. `DomainQueryService` (DQS) — только чтение, не зависит от транспорта. Сервисы могут принимать `Loader<T>`. Story и UseCase остаются в стандартном смысле (входной сценарий UI и прикладная операция). Между Policy и DCS — декларативные доменные правила (D-40).

**D-07. `ReadonlyAr<T>` и изоморфный домен.** Мутирующие методы Ar всегда возвращают `Result`, методы-вопросы — никогда; `ReadonlyAr<T>` выводится типом без ручного кода. Фасады, транспорт и UI получают снапшот и восстанавливают Ar локально как `ReadonlyAr`.

**D-08. UC только техничен.** Загрузить → Policy → операция домена (Ar / DCS) → зарегистрировать в UoW. Никаких доменных решений (`if` по состоянию, статусам, входу).

## Контракты и связи

**D-09. Модули и фасады — стратегический уровень.** У каждого модуля есть `defineModule` (паспорт, `dependsOn`) и фасад — runtime-API модуля для других модулей (без манифеста, D-42; `Facade<M>`, D-43). Фасады возвращают `Result`.

**D-10. Ссылки вместо строк, FQN для событий.** Манифесты ссылаются друг на друга объектами. Имя события — `module.aggregate.event` (`todo.task.completed`).

**D-11. Граф L0 / L1 / L2.** L0 — карта модулей, L1 — модуль, L2 — агрегат. Каскад проходит сквозь уровни.

**D-12. Декларация + верификация.** Каждая декларация проверяется типом, рантайм-ассертом в test/dev или контрактным тестом. Правило без проверки — пожелание.

## Ошибки и сохранение

**D-13. `Result<T, E>` вместо `throw` для штатных отказов.** `throw` — только баг, инвариант, системный сбой. См. [errors-result.md](./errors-result.md).

**D-14. Ошибка не знает транспорт.** У ошибки есть `code` и нейтральный `kind`; маппинг в HTTP / MCP / текст бота — в адаптерах. Ошибки зависимостей пробрасываются по ссылке через контракт фасада.

**D-15. Unit of Work в `dmg-core`.** UC регистрирует изменённые агрегаты в UoW; базовый класс после `Ok` фиксирует изменения и публикует события агрегатов. JSON-реализация не атомарна — осознанный техдолг до смены хранилища.

**D-16. Время — `Timestamp` (number, мс, UTC).** Переходные схемы читают ISO-строку, пишут число; пакетная миграция данных — забота проекта.

## Транспорт

**D-17. HTTP — JSON-команда.** `POST /api/<module>` с `{ uc, input, meta? }`; `OPTIONS` отдаёт контракт модуля. См. [transport.md](./transport.md).

**D-18. MCP из манифестов.** UC → tools, граф → resources. Старт: только query, dev, заданный актор.

## Вызовы, границы и проверки

**D-25. `Caller` — кто вызывает.** Четыре подтипа: `guest`, `user`, `delegate`, `system`. Def UC объявляет `callers`; домен видит субъекта (для `delegate` — замещаемого), аудит — исполнителя через meta событий. Тип и `callers` — в `dmg-core`, делегирование — модуль приложения. См. [caller.md](./caller.md).

**D-28. Модуль готов к выносу в сервис.** Межмодульно — только асинхронные фасады и события по Def; один UoW — один модуль; реакции идемпотентны, публикация через outbox; `Caller`, `Trace`, конверт события и снапшот Ar сериализуются в JSON. Модулю в другом репо нужны только контракты зависимостей (`domain/<m>/contract`), не весь домен. Сервис из одного модуля — то же приложение с одним модулем в `dependsOn`.

**D-32. Архитектурные правила — в biome.** Импортные границы (ARC) — `noRestrictedImports`, остальные (DOM-01/11/12/14, ERR-01, API-02, CODE-02) — GritQL-плагины в `overrides`. Какие пути блокируются, решает проект (старый код можно исключить или перевести в `warn`). Правила проверяются тестом на фикстурах-нарушителях, поэтому ослабить правило незаметно нельзя.

**D-33. Подпути `dmg-core` по слоям.** Корень — ядро и манифесты домена (`Result`, ошибки, `F`, `define*`, `Aggregate`, Policy): чистый код, единственное, что видит домен. `dmg-core/app` — исполнение (UC/ER/Job по Def, модуль, UoW, шина, след), `dmg-core/graph` — нормализация и граф, `dmg-core/arch` — проверки, `dmg-core/testing` — хелперы. Граница проверяется lint (ARC-02 для домена, ARC-11 внутри пакета). UI-манифесты — отдельным пакетом, не подпутём.

**D-34. Время — аргумент операции, часы — порт приложения.** Домен не читает часы: момент передаётся в операцию Ar (`create(input, at)`, `complete(at)`), `updatedAt` ставит база из того же `at`. Часы — `AppContext.clock` (`Clock`, `systemClock`); UC/ER/Job берут момент через `this.now()`, UoW — для `occurredAt`. Глобального изменяемого состояния нет: в тестах часы задаёт `testAppContext({ at })`; приложение может передать свои часы (мост к старому коду).

**D-35. Жизненный цикл агрегата — в Def.** Переход объявляет `from`, `to` и `rejects` (ошибку для каждого статуса вне `from`, полноту проверяет компилятор, принадлежность группе агрегата — MAN-12). Ar меняет статус только через `transition(op, at, apply)`, база возвращает отказ из Def и ставит `to`; `change` статус не трогает. Граф L2 получает операции с их отказами без разбора кода методов.

**D-36. Версия агрегата — оптимистичная блокировка.** `BaseEntityFields.version` растёт с каждой мутацией Ar (записи без поля читаются как 0, миграция данных не нужна; так же запись без `updatedAt` читается как `updatedAt = createdAt` — фолбэк в `def.state` агрегата, поэтому сырые данные разбираются `<Agg>ArDef.state`, а не экспортированной схемой). Репозиторий при `save` сверяет версию в хранилище со `storedVersion` агрегата и при расхождении бросает `VersionConflict`; UoW превращает его в базовую ошибку `VERSION_CONFLICT`; события публикуются только у агрегатов, записанных до сбоя (они не откатываются, D-15). Новый агрегат (из `create`, база — `Aggregate.newState`, D-43) отличается от записи версии 0: `create` с занятым uuid — конфликт, старая запись не перезаписывается. Атомарность чтения-сверки-записи — забота хранилища (JSON — `createLock` в процессе). Откат уже записанных агрегатов UoW не делает (D-15).

**D-37. Внешний модуль — контракт без реализации.** Модуль, реализованный вне приложения (ещё не переведённый код или другой сервис, D-28), описывается `defineModule({ external: true })` в своём `contract.ts`: агрегаты с событиями, фасад, Def UC без реализации (D-42), без ER/Job. На него можно ссылаться в `dependsOn` и подписываться на его события; MAN-06 считает их опубликованными внешней стороной. События старого кода доставляет мост приложения (старое имя → Def, перевод payload, проверка схемой, сбой — в production `warn`). При переводе модуля на Def `external` снимается, контракт остаётся.

**D-38. ~~Фасад модуля — только по потребителю.~~ Заменено D-42** (фасад без манифеста). Модуль объявляет `defineFacade` только когда фасад нужен другому модулю (вызов из UC/ER/Job по `calls`, ARC-04); спекулятивное API не заводится.

**D-39. Доступ к state: решение — только Ar, форма — в контрактах, показ — в рендерере.** Уточняет D-05. Разводятся три вида доступа к state агрегата:
- **решение** (ветвление по полям) — только Ar: методы-вопросы и операции; остальные (UC, ER, Job, Story, Policy, доменные правила, DCS, DQS, фасады) получают `ReadonlyAr` и спрашивают его;
- **форма** (схема) — Def контрактов своего модуля (вход и выход UC, payload событий, проекции DQS, фасад) выводят схему из state (`v.pick`/`v.omit`), а не копируют поля вручную; чужой модуль state не импортирует;
- **показ** (чтение полей для отображения) — только рендереры UI; Story передаёт данные рендереру и полей для решений не читает.

Репозиторий — `restore`/`snapshot` и ключи хранения; тесты и фикстуры строят агрегат через `create`/`restore`. Геттер на поле Ar — только для идентификаторов (`uuid`, связи): данные, нужные контракту ошибки или выхода, отдаёт метод Ar, который строит этот контракт (Ar владеет ошибками своей группы). Lint DOM-01 разрешает импорт `…/state` файлам Def контрактов своего модуля.

**D-40. Доменное правило — декларативно, без субъекта; Policy — только права субъекта.** Критерий выбора — **участвует ли в ответе субъект** (caller), а не число агрегатов:
- **Policy** — «может ли этот субъект?»: контекст может содержать несколько агрегатов (владелец этой задачи и проект, в котором она лежит); отказ — `ACCESS_DENIED` (`kind: access`) с `denyMessage`.
- **Доменное правило** — «допустимо ли действие при текущих состояниях агрегатов?» (уникальность, допуск к следующему модулю): ответ не зависит от того, кто спрашивает. Объявляется декларативно по образцу `rule` — имя, `label`, `description`, ссылка на `ErrorDef` своей группы, проверка над `ReadonlyAr`/значениями — и возвращает `Result<void, Err>` с payload ошибки, а не `Decision`. Def UC ссылается на правила рядом с `policy`, правила видны в манифесте и графе.
- **Переход Ar** (`rejects` в `defineAggregate`) — частный случай доменного правила в пределах одного агрегата; остаётся в Ar.

DCS остаётся для мутаций нескольких агрегатов и композиции правил с операциями. Композиторы (`allOf`/`anyOf`) для доменных правил — только по потребителю.

Форма API: `domainRule({ name, label, description, error, check })` в группе `<A>Rules = defineRules({ name, label, description, rules })`, файл `<aggregate>.rules.ts` (с трека `dmg-core-oop` — `DomainRuleDef.define` и `RulesDef.define`, [manifests.md](./manifests.md) §1). Def UC — `rules: [...]` рядом с `policy`; исполняет `UseCaseFromDef` над результатом `load` после Policy (`load → Policy → rules → execute`). Ошибка правила объявляется в `errors` UC явно — `ArchChecker` ловит пропуск.

**D-42. Межмодульная связь в манифестах — «UC → UC»; фасад — рантайм-граница без манифеста.** Заменяет D-38, уточняет D-09. Вызывающий `module`, ответственность фасада и рантайм-проверка `calls` — заменены D-43.
- **Связи объявляются один раз:** `dependsOn` у модуля и `calls` у UC/ER/Job — Def UC других модулей (из `dependsOn`). Граф строит рёбра «UC → UC» из `calls`; последствия вызова (агрегат, `emits`, дальше по ER) выводятся из Def вызываемого UC; command-цель — межмодульный побочный эффект, место которого выбирает владелец проекта по каждому случаю ([use-case.md](./guides/use-case.md) §1). Фасадов в манифестах и графе нет (`defineFacade`, `method`, `facade` в `defineModule` уходят).
- **Фасад остаётся в рантайме** — граница модуля: вызывающий модуль не знает реализации владельца (in-proc сейчас, сетевой клиент при выходе в отдельный сервис — вызывающий код не меняется). Тип фасада — TS-тип в домене модуля-владельца (`<m>.facade.ts`, не Def), реализация — в его пакете.
- **Ответственность фасада** (форма заменена D-43: `Facade<M>.handle` без методов-обёрток, `ReadonlyAr` строит вызывающий): обёртка над UC своего модуля — каждый метод вызывает UC; допустимы несложные преобразования входа и выхода (собрать вход, выбрать поле, свести ответ), доменных решений нет (их делает UC и домен владельца). Выход UC, который является state агрегата (один или массив), фасад отдаёт как `ReadonlyAr<T>` (`ReadonlyAr<T>[]`) — клиент получает готовый агрегат. Ошибки метода — ошибки вызываемого UC (`Result`), фасад их не прячет и не придумывает.
- **~~Вызывающий `module`.~~ Заменено D-43.** Фасад вызывает UC от вызывающего вида `module` (его обязанность — подставить его): `from` — Def UC/ER/Job, который вызвал фасад, `origin` — исходный вызывающий; субъект (`subjectOf`) — субъект `origin`, Policy вызываемого UC проверяется. UC, доступный другим модулям, объявляет `module` в `callers`, иначе — `UNAUTHORIZED`.
- **Проверки:** `ArchChecker` — UC в `calls` из модуля в `dependsOn`, не свой; ~~рантайм — вызываемый UC отказывает (`UNAUTHORIZED`), если его Def нет в `calls` у `from`~~ (заменено D-43: типом `call`). Ревьюер — фасад без доменных решений.
- **Внешний модуль (D-37)** объявляет Def UC без реализации; приложение исполняет их адаптером над старым кодом или сетевым клиентом; при переводе модуля Def получает реализацию, адаптер уходит.

**D-43. Вызовы и граница модуля: `Caller`-классы, модуль — единственная точка входа, типизированный `call`.** Заменяет в D-42 вызывающий `module` и рантайм-проверку `calls`; остальное в D-42 в силе.
- **`Caller` — иерархия классов** (`GuestCaller`, `UserCaller`, `DelegateCaller`, `SystemCaller`) с `subject()`, `person()`, `toLog()`. Вызывающего `module` нет: межмодульный и внутренний системный вызов — один `SystemCaller(from: OperationRef, person?)`, где `from` — `{ kind, module, name }` вызвавшей операции, `person` — исходный человек (`caller.person()` пришедшего, матрёшки нет). ER и Job — без `person`. `channel` — в `Trace.channel`, не в `GuestCaller`. Подробно — [caller.md](./caller.md).
- **Policy — только субъект, вызывается всегда** (`Rule.evaluate(subject, ctx)`): вид вызывающего она не знает, `delegable` нет. Вид отсекает `callers` (`UNAUTHORIZED`). Системный вызов без субъекта — явно: отдельный UC (`callers: ['system']`, `allowAll`) или переопределение `protected checkPolicy` в наследнике. Шаги `UseCaseFromDef` — `protected`: `checkCaller` → `parseInput` → `load` → `checkPolicy` → `checkRules` → `execute` → `parseOutput` → фиксация.
- **Модуль — единственная точка входа:** `ModuleFromDef.handle(def, input, caller, trace)` и `runJob`; `useCase(def)` не публичный. Транспорт и фасад ходят только через модуль.
- **Фасад** — `Facade<M>` в домене (`handle` только UC с `'system'` в `callers`, вызывающий — `SystemCaller`) и `ModuleFacade<M>` в `dmg-core/app`, обёртка над `ModuleFromDef.handle`. Свои типы фасадов модулей и методы-обёртки не заводятся; наследник `ModuleFacade` — только ради удобных методов поверх `handle`. Выход — как у UC; `ReadonlyAr` строит вызывающий (`Aggregate.readonly(state)`). В тестах — `StubFacade<M>` (`dmg-core/testing`).
- **`OperationFromDef`** — база UC/ER/Job: `now()`, `createUow(caller, trace)`, `protected call(def, input, caller, trace)` — только Def из `D['calls']` (по типу — UC с `'system'` в `callers`), через `ModuleFacades` в `deps` с `SystemCaller(this.ref, caller.person())`. Рантайм-проверки `calls` нет (тип + `ArchChecker`), `UNAUTHORIZED` без `from`. Ошибки ядра чужого UC проходят насквозь (`UseCaseErrorOf<D>`), доменные — объявляются в `errors` своего UC или переводятся.
- **Лог операций** (`OperationLog` в `AppContext`): запись `OperationRecord` (вызывающий `toLog()`, `trace`, вход, результат, события, длительность) пишет `OperationFromDef` последним шагом при успехе и отказе; `uow.commit()` возвращает опубликованные события. Хранение — реализация приложения (например, JSONL по дням), `input`/`output` с порогом размера. `caller` из конверта события удалён: аудит «кто» — через запись породившей операции (`trace.cause`).
- **Функции → объекты:** класс `Trace` (`fromRequest`, `fromEvent`, `forJob`) вместо `requestTrace`/`incomingRequestId`; `Aggregate.newState(uuid, at)` вместо `newEntity`; `Aggregate.readonly(state)` вместо `asReadonlyAr`.

**D-44. Состояние агрегата наружу — `view()`; `snapshot()` — только репозиторий.** Уточняет D-05 и D-39. `Aggregate.view()` отдаёт состояние тем, кому разрешён к нему доступ: выход UC (query), рендерерам UI, показывающим текущее состояние, и другим местам по тому же основанию. По умолчанию `view()` возвращает `snapshot()`; агрегат может переопределить его (скрыть или преобразовать поля). `snapshot()` вызывает только репозиторий (и его тесты/фикстуры) — для записи; больше никто. Данные для контракта ошибки или выхода, которые не являются состоянием, — по-прежнему метод Ar, строящий контракт (D-39).

**D-45. Вход модуля для остального кода — `contract`; state — внутри модуля.** Уточняет D-37, D-39, D-42, D-44. У модуля домена два входа:
- **`contract.ts`** — единственный вход для остального кода: другие модули (домен и прикладной слой), входные адаптеры (UI, stories), скрипты, транспорт и фронт. В нём только объявления: `<M>ModuleDef`, Def операций, которые вызывают снаружи, группы событий и ошибок, схемы и типы VO, входящие в эти Def. Классов (Ar, Policy, DCS/DQS), Def агрегатов и схем entity в нём нет.
- **`index.ts`** — API домена для своего прикладного пакета: всё, включая контракт.
- **State — внутренний.** Его видят Ar, Def своих контрактов (вывод схем, D-39) и репозиторий через `ArDef.state`. Подпути state у пакета домена нет. Остальной код получает форму данных из контракта: выход UC, payload событий, данные ошибок. Внутри модуля — `view()` (D-44). Фронт и транспорт знают только схемы контракта, поэтому смена state не ломает клиентов, пока контракт выводится тем же.
- **Домен другого модуля нужен — пополняется контракт.** Экспорт добавляется в `contract.ts` с JSDoc «кто и зачем». Так использование домена вне модуля явное (экспорт), определённое (одно место) и проверяемое (ARC-04).
- **Проверка.** ARC-04: чужой модуль из любого места (домен, прикладные пакеты, адаптеры, скрипты) — только `<domain>/<m>/contract` (в домене — ещё и только из `dependsOn`). Для модуля на Def (не `external`) нарушение блокирует в обе стороны: он импортирует чужие только через контракт, его импортируют только через контракт. Состав `contract.ts` — review.

**D-46. `Caller` и `Trace` переходят границу процесса как JSON.** Удалённый вызов фасада (модуль в другом сервисе, D-28) передаёт `caller` и `trace` в JSON: `toJSON()` у отправителя, статический `fromJSON()` у получателя восстанавливает классы. Субъект `U` едет **целиком**: он обязан быть простыми данными (plain JSON), а получатель доверяет отправителю (внутренние сервисы). Если у приложения `U` — класс, `fromJSON` принимает необязательный `revive(json) => U`. Вложенный вызов, как и раньше, — `SystemCaller(from, person)`; в JSON он несёт `person` со своим `U`. Тест «круг через JSON» охватывает все виды `Caller`, `Trace`, конверт события и снапшот Ar. Форма для лога (`toLog()`, только id) не меняется. **Внутри одного процесса сериализации нет:** in-proc фасады получают объекты как есть; `toJSON`/`fromJSON` вызывает только адаптер удалённого фасада, а тест круга гарантирует, что вынос модуля не сломается.

**D-47. Публикация — через outbox, доставка — с отсевом повторов.** UoW после записи агрегатов передаёт конверты не в шину, а в порт `Outbox` (`AppContext`); до шины их доставляет relay. По умолчанию outbox in-proc: конверт сразу публикуется в шину, поведение то же, что до D-47. Персистентный outbox — реализация потребителя. Реакции получают событие через порт `Inbox`: повторная доставка того же `eventId` той же реакции отбрасывается (in-proc реализация по умолчанию). Повтор с новым `eventId` (тот же факт, опубликованный дважды) — забота домена; для него `dmg-core/testing` даёт контрактный хелпер «событие доставлено дважды → второй раз эффекта нет».

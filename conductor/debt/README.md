# Долг проекта

**Назначение:** правила учёта долга u7-school и три реестра. Долг не привязан к треку: заводят и гасят его разные треки.

| Реестр | ID | Что в нём |
|---|---|---|
| [code.md](./code.md) | `C-DEBT-<n>` | временные нарушения целевой архитектуры в коде |
| [tests.md](./tests.md) | `T-DEBT-<n>` | лишние и дублирующие тесты, ждущие чистки |
| [product.md](./product.md) | `D-DEBT-<n>` | технические пробелы продукта: функции нет или она неполна |

Концептуальное развитие продукта — не долг, оно в [roadmap.md](../roadmap.md). Долг кода пакета `dmg-core` — в его собственном `debt.md` (корень репо пакета) с ID `DEBT-<n>` без префикса. Префикс `C-` у долга кода проекта разводит нумерации: один и тот же номер в двух репо уже приводил к путанице. Голый `DEBT-<n>` в проекте — всегда запись пакета.

---

## 1. Общие правила

- **Только открытый долг.** Закрытая запись удаляется из реестра; единственный её след — коммит `закрыть <ID>` (например, `refactor(wish): закрыть C-DEBT-40`). Заголовков «погашен», «слит в» и журналов закрытого нет.
- **Номера не переиспользуются.** Новый ID — следующий после строки «Последний выданный ID» в шапке реестра; строка правится в том же коммите, что и новая запись.
- **У записи есть владелец или триггер** — ровно одно из полей:
  - **Погашает** — трек-владелец (существующий или кандидат из `roadmap.md`);
  - **Триггер** — наблюдаемое условие, при котором долг пора гасить (рост данных, появление второго потребителя, жалоба). «Когда-нибудь» — не триггер.
- **Разбор долга** — в конце каждого трека и перед релизом. Orchestrator проходит по трём реестрам:
  - запись, чей владелец — закрываемый трек, погашена или получает нового владельца либо Триггер;
  - сработавший Триггер — запись уходит в план ближайшего трека или Нурболату на решение;
  - запись без владельца и Триггера — ошибка разбора.
- **Тактические решения отдельным журналом не ведутся.** Решение, несущее знание для будущей работы, — в `decisions.md` (проекта или пакета) или гайд; временный код — запись `C-DEBT-<n>`.
- Ссылаться на запись из документов можно; ID закрытой записи при закрытии из документов убирается.

## 2. `C-DEBT-<n>` — долг кода

Реестр — **allowlist**: код к записи привязывают её поля, а не маркеры в коде.

```
### C-DEBT-<n>: <краткое название>
- **Место:** `<glob>`, `<glob>` — <пояснение>
- **Признак:** `<регулярка>`
- **Корень:** `<glob>`
- **Причина:** <почему нельзя убрать сейчас>
- **Погашает:** <трек>            ← или **Триггер:** <условие>
- **Критерий снятия:** <что должно исчезнуть>
```

- **Место** (обязательно) — где долг допущен: glob'ы в бэктиках подряд через запятую в начале строки поля или пунктами первого уровня под ним; после glob'ов — пояснение. Внутри записи нет пустых строк между полем и его пунктами и нет заголовков.
- **Признак** (обязательно) — регулярка (JS, флаг `m`) в бэктиках, которой долг выражен в коде.
- **Корень** — glob области, где признак вне Места — новый долг без записи. Нет поля — весь проверяемый код. Исключения — перечислением в `{…}` (Bun.Glob не знает `!` и не разворачивает `/` внутри `{…}`).
- Проверяемый код — исходники пакетов (`{platform,modules,authoring,runners}/*/src`, `domain/src`, вместе с их тестами) и `scripts/` без тестов скриптов.

`bun run arch:check` по каждой записи:

- glob Места не находит файлов — устаревшее место;
- признака нет ни в одном файле glob'а — долг погашен: сними glob или закрой запись;
- признак в файле Корня вне Места — долг без записи: заведи запись или расширь Место.

Ещё два правила проверки:

- `C-DEBT-<n>` в коде — только в строке `biome-ignore` (текст причины) и только ID записи из реестра; голые `// C-DEBT-<n>` и упоминания в JSDoc — ошибка.
- **Маркер временности без записи — ошибка.** Строка с «Временное решение», «Уходит с миграцией» (без учёта регистра) или «ВРЕМЕННЫЙ» (только заглавными) допустима лишь в файле из Места записи. Область — исходники пакетов (`*/src`, `domain/src`, с тестами), без `scripts/`.

Погашение части долга — снять glob из Места. Закрытие — удалить запись и `biome-ignore` с её ID одним коммитом.

## 3. `T-DEBT-<n>` — долг тестов

Правило — TST-08 и D-66 пакета (`node_modules/dmg-core/docs/reference/testing.md` §5): при переносе кода тесты переезжают, а не копируются.

```
### T-DEBT-<n>: <что лишнее>
- **Файлы:** `<glob>`, `<glob>` — <строки, имена тестов>
- **Дублирует:** <что и где проверено ещё раз>
- **Решение:** <чем закрыть: удалить, свести, оставить одно>
- **Погашает:** <трек>            ← или **Триггер:** <условие>
```

- **Файлы** обязательно; проверка — каждый glob находит хотя бы один файл (иначе случай уже почищен или файл переехал).
- Дубли в коде текущего среза чистятся в срезе и в реестр не попадают; в реестр идёт накопленное вне среза.
- Почищенный случай удаляется из реестра; число удалённых тестов — в `summary.md` трека, который их почистил.
- Пополнение: ревьюер и авторы пишут в отчёте строку «Кандидат в чистку тестов: файл — что дублирует» (роль `dmg-reviewer`); orchestrator заводит запись. Случай с новым признаком — ещё и строка в каталоге §3.1; если из него следует правило — правка `testing.md` пакета или проектного документа.

### 3.1. Признаки лишнего теста

Проблема: при рефакторинге функционал не меняется, а число тестов растёт. Корень — перенос превращается в копирование: «поведение вызывающего не изменилось — его тесты не трогаем».

Вопрос к тесту: **«какая реальная ошибка в коде модуля уронит этот тест и только его?»** Нет такой — кандидат.

**А. Одно правило — несколько мест**

| ID | Закономерность | Признак |
|---|---|---|
| Б-1 | Правило проверено уровнем ниже и повторено выше (UC ↔ Ar/DQS/Policy, story ↔ резолвер) | `it` UC без загрузки, Policy, своей ошибки, записи в UoW |
| Б-2 | Вопрос Ar проверен своим `it` и через единственного потребителя | метод Ar с одним вызывающим, тест вызывающего ловит инверсию |
| Б-3 | Общий хелпер проверен в каждом вызывающем | одинаковое тело `it` в нескольких файлах раздела |
| Б-4 | Integration/e2e дословно повторяет unit-тест story | совпадают имена `test(...)` и строки экрана |
| Б-5 | Файл-двойник после переезда: старый файл тестов не удалён или «новое поле» — новым файлом | `*.student.test.ts`, `*.roster.test.ts`, «Заменяет ожидания…» |
| Б-6 | Копия соседнего теста без нового класса входа; строка таблицы конфигурации — отдельным `it` | `it.each` по параметру, который код не читает; по `it` на шаг одного обработчика |
| Б-14 | Файл-паспорт UI-экранов: точные тексты и коды всех кнопок фичи отдельным файлом — падает от косметики; ценны только `callback_data` (сводить к реестру кодов) | `flatButtons(`, имена `S01…`, файл `inventory.test.ts` в `stories/` |

**Б. Проверяется не код модуля**

| ID | Закономерность | Признак |
|---|---|---|
| Б-7 | Ручной паспорт Def — дубль `arch:check` (состав `errors`/`emits`/`calls`, реэкспорт ключами) | `normalize(`, `ArchChecker` в тестах модуля |
| Б-8 | Схема платформы: приём/отказ `F.uuid`, `picklist`, `variant`, `expectedVersion` | `safeParse`/`v.parse` на Def-схемах |
| Б-9 | Поведение платформы: `UNAUTHORIZED`, `VersionConflict`, изоляция Job, умолчания story бота, «событий нет» отдельным `it` | `menuButtons` пусто, «Неизвестная команда», `published).toEqual([])` |
| Б-10 | Тест фейка, стаба или фикстуры (фильтр выборки делает фейк; «поток засеялся») | «чужие записи не затронуты», id фикстур |
| Б-18 | Тест Def в домене (`domain/src/<m>/**/uc/*.uc.test.ts`) дублирует тест реализации того же UC в модуле: пайплайн разбирает вход и выход схемами Def на каждом вызове. Своя логика схемы — в тест UC модуля | пара `domain/…/uc/<uc>.uc.test.ts` ↔ `modules/…/uc/<uc>.uc.test.ts` |
| Б-19 | Рендер платформы в тесте владельца: `it` на каждый уровень экрана проверяет разметку после `presentNavLevel` — её держит `presenter.test.ts` UI-ядра. Остаётся один smoke «резолвер → презентер» | `describe('Подключение presenter…')`, `keyboard.rows[N]`, экранированные строки |

**В. Тест не может упасть**

| ID | Закономерность | Признак |
|---|---|---|
| Б-11 | Тавтология: константа ↔ та же константа, ожидание посчитано тем же продовым кодом, однострочный геттер | `const expected = new <ProdClass>`, FQN/код ↔ свой литерал |
| Б-12 | Пустой вход → пустой результат на `filter/map` | «… нет — пусто» |
| Б-13 | Тест мёртвого экспорта или мёртвого входа контракта — сигнал удалить код, а не только тест | экспорт без импортов вне своего теста; поле `input` Def, которое `execute` не читает |
| Б-15 | Тест-некролог переезда: проверяет, что удалённых имён и кодов больше нет | `not.toHaveProperty`, `not.toContain` по старым кодам |
| Б-16 | Имя шире проверки: заявлены две ветки, проверяется одна (переписать, не удалять) | «и» / «или» в имени, один вызов в теле |
| Б-17 | Позитивный тест типа: вывод, который уже использует рабочий код. Правило — TST-10 пакета (D-68) | `expectTypeOf(`, `Equal<`, `toEqualTypeOf` |

**Корни.** (1) Перенос копирует тесты вместе с кодом; (2) тесты первого шага TDD (схема, паспорт) остаются как «контракт»; (3) образец эталона размножается копированием; (4) правило «Схемы — все поля» само порождает Б-8; (5) нет правила «один сценарий — один файл».

**Не кандидаты.** Тесты, охраняющие инвариант данных при чтении (строгое чтение `courses.json`), и тесты вариантов модели, которые различает только тест (курс без этапов / один / несколько этапов).

## 4. `D-DEBT-<n>` — технические пробелы продукта

Функции нет или она сделана не до конца, и это известно: путь, который сегодня закрывается ручной операцией, проверка, которой не хватает до следующего шага продукта. Признака в коде у такой записи нет — проверяется только формат.

```
### D-DEBT-<n>: <чего нет>
- **Суть:** <что не работает или отсутствует и как обходятся сейчас>
- **Причина:** <почему не сделано>
- **Погашает:** <трек>            ← или **Триггер:** <условие>
- **Критерий снятия:** <что должно появиться>
```

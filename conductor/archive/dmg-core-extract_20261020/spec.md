# Спецификация: dmg-core-extract — платформа DMG как внешний пакет `dmg-core`

## Обзор

Трек #1б из migration.md (после [core-dmg](../../archive/core-dmg_20261018/spec.md)). Платформа DMG (`packages/core/src/dmg`) становится самостоятельным пакетом **`dmg-core`** (npm), который можно вынести в отдельный репозиторий и ставить как внешнюю зависимость. Параллельно закрепляется готовность модулей к выносу в отдельные репо и сервисы ([D-28](../../architecture/decisions.md)).

## Решения

- **Выносим только DMG, legacy остаётся.** Legacy-часть `@u7-scl/core` (`domain/api/ui/shared/infra`) исчезнет вместе с переходом (legacy.md §6) и в `dmg-core` не попадает.
- **Мосты к legacy — на стороне монорепо.** 6 файлов `dmg/app/**/legacy-*`, `run-logged`, часть `use-case-from-def` и `context` зависят от `#*-legacy`. Они уезжают в `@u7-scl/core` (подпуть `legacy-bridge`) и зависят от `dmg-core`, не наоборот. `dmg-core` не знает о legacy.
- **Установка — из npm по semver.** До первой публикации и в разработке — workspace-пакет `packages/dmg-core` плюс проверка `bun pm pack` в чистом каталоге. Никаких git-зависимостей и `bun link`.
- **Алиас внутри пакета — `#core/*`** (вместо `#dmg/*`), так как после выноса `src/dmg` станет `src`. Переименование — одним скриптом.
- Имя `dmg-core` свободно на npm (проверить перед публикацией).

## Порядок относительно других треков

Трек делится на две части с паузой между ними; на этот раздел ссылаются планы соседних треков (`generators`, `domain-package`, `golden-wish`).

1. **Часть А — Фазы 1–3** (развязка, пакет `dmg-core`, самодостаточность). Выполняется **до** `generators`. После Фазы 3 путь пакета (`packages/dmg-core`), имя импорта (`dmg-core`, `dmg-core/testing`) и алиас `#core/*` **финальные**: генераторы и эталонный модуль пишутся на них без переименований.
2. **Пауза.** После контрольной точки Фазы 3 трек остаётся открытым (`tracks.md`: `[~]`), работа переходит к `generators`, затем `domain-package` и `golden-wish` (migration.md §2).
3. **Часть Б — Фазы 4–6** (готовность к распределённому запуску, документация и инструменты в пакете, вынос и публикация). Стартует **после** `golden-wish`: контракты `domain/<m>/contract` требуют `domain-package`; outbox и идемпотентность реакций проверяются на реальном модуле; гайды Фазы 5 пишутся по эталону.

**Что гарантирует часть А соседним трекам:** `dmg-core` не импортирует legacy и `@u7-scl/*` (ARC-10); legacy-мост `packages/core/src/legacy-bridge` остаётся рабочим для `wish`, пока тот на legacy-шине и legacy-`Job`; `bun run check` включает `extract-check`.

**Что соседние треки не делают:** не меняют публичную поверхность `dmg-core` без записи в этом треке; не удаляют `legacy-bridge` до конца миграции.

## Функциональные требования

**Ф1. Развязка.** `dmg-core` без импортов из `*-legacy` и `@u7-scl/*`; правило проверяется `arch:check`/biome. Единственные внешние зависимости — `valibot`, `@valibot/to-json-schema` (peer).

**Ф2. Пакет.** `packages/dmg-core`: `name: dmg-core`, не `private`, `exports` (корень, `testing`, `arch`), `files`, `engines`, `sideEffects: false`. Тестовое (`bun:test`) — только в подпути `testing`. Корневые `paths` убраны, потребители подключают пакет как обычную зависимость.

**Ф3. Самодостаточность.** Свои `tsconfig`, `biome.json`, скрипты `check`. Скрипт `scripts/extract-check.sh` копирует пакет в пустой каталог, ставит зависимости и гоняет `check`; входит в `check` монорепо.

**Ф4. Готовность к распределённому запуску** (закрепляется тестами, а не только текстом):
- Реакции идемпотентны; публикация событий — через outbox-порт (интерфейс в `dmg-core`, реализация потребителя).
- Один UoW — один модуль; межмодульные изменения только через фасад/событие.
- `Caller`, `Trace`, конверт события и снапшот Ar проходят круг через JSON без потерь (тест).
- Контракты модуля (фасад, события, ошибки) выделяются из единого `@u7-scl/domain` отдельным подпутём `domain/<m>/contract`, чтобы зависимый модуль в другом репо брал только их.

**Ф5. Документация и инструменты в пакете.** Главная цель: потребитель `dmg-core` получает полный комплект для разработчика и агента. В пакет входят:
- `docs/` — документация платформы (манифесты, ошибки и `Result`, `Caller`, тестирование, моделирование домена, TypeScript, нейминг, слои, каталог правил с ID) и `llms.txt` — индекс для LLM;
- `skills/dmg-architecture` — как писать модуль на DMG;
- `agents/` — роли `domain-author`, `api-author`, `reviewer` для Claude Code и pi (из `.agents-core/roles`);
- CLI `dmg-core init` / `sync` / `sync --check` — доставка скилов и ролей в проект потребителя и контроль их актуальности по версии.

В проекте остаётся специфичное: `legacy.md`, `migration.md`, `agents.md` (процесс), conductor-скилы, `migrator`, решения по данным. Источник правды по платформе — один, в репозитории пакета.

**Ф6. Готовность к выносу** (Нурболат, 2026-10-26: сейчас не выносим и не публикуем). Вынос сводится к переносу каталога `packages/dmg-core`: пакет несёт свои lint-правила, их тест и сквозную проверку потребителя (`bun run e2e` — будущий CI), `npm publish --dry-run` проходит без исправлений, лицензия MIT (автор — Nur). Сам вынос — по чек-листу ниже, отдельным треком после релиза u7-school.

## Разметка: что в пакет, что остаётся в проекте (Фаза 5)

Язык документации пакета — русский (Нурболат, 2026-10-26). Перенесённые файлы из `conductor/architecture/` удаляются, проект ссылается на `packages/dmg-core/docs/` (после Ф6 — `node_modules/dmg-core/docs/`). Образец в гайдах — учебный модуль `src/testing/example` (todo/users), обогащается задачей Ф5 по slices/example-enrich.md.

**Нейтрализация** при переносе: `packages/domain/src/<m>` → «пакет домена» (`<domain>/<m>`), `packages/<m>/src` → «прикладной пакет модуля», `apps/*` / бот → «входной адаптер», `wish` → `todo`/`users`, `@u7-scl/*` → «пакеты приложения», `bun run check` → «`check` проекта». Абзацы про legacy, strangler, переход и бота — остаются в проекте (в `legacy.md`, `migration.md`, `ui/`), в пакете их нет.

**Решения по открытым вопросам (Нурболат, 2026-10-26):**
1. Генераторы переезжают в пакет: `dmg-core gen <вид> …`, раскладка — из `ArchApp.layout` проекта; `scripts/gen` проекта удаляется (задача Ф5). `naming.md` §5 — в пакет.
2. Роли: `dmg-core init`/`sync` копируют роли пакета (`agents/`) в `.agents-core/roles/` проекта как базу; проектный блок (гейт, `conductor/`, автономный режим) остаётся в `.agents-core/common.md` проекта и дописывается `agents:sync`. `migrator` — только проектный.
3. Доставка агентов (Нурболат, 2026-10-26) — по решению 2, но в общем виде: **пакет не знает ни раскладки u7-school, ни того, какие агенты работают в проекте-потребителе.** `dmg-core init`/`sync` — общий инструмент «быстро и удобно подключить нужное»: проект сам выбирает, какие роли и скилы взять и куда их положить (каталог-источник ролей, каталоги скилов по средам, файл для вставки со ссылкой на `llms.txt`); у каждого параметра — разумное значение по умолчанию. В пакете нет путей `.agents-core`, `conductor/`, имён проектных ролей и знания о сборщиках проекта (`agents:sync`). Подключение в u7-school (`.agents-core/roles/` как база, `.agents-core/common.md` дописывает `agents:sync`, `migrator` — проектный) — отдельный шаг поверх общего инструмента.
4. Форма `init`/`sync` (Нурболат, 2026-10-26): настройки — файл `dmg-core.json` в корне проекта (`init` создаёт его со значениями по умолчанию); роли доставляются в список целей `{ dir, format: neutral | claude | pi }` (по умолчанию — копии для Claude Code в `.claude/agents`); для `neutral` общий блок пакета (`agents/common.md`) кладётся отдельным файлом (`common` цели), чтобы сборщик проекта приклеивал его ко всем ролям, включая проектные. Сопоставление нейтральных инструментов со средами — в пакете.
5. Генераторы (Нурболат, 2026-10-26): раскладка для `dmg-core gen` — секция `gen` в `dmg-core.json`: шаблоны с `{m}` — `domain` (каталог модуля домена), `app` (каталог прикладного слоя модуля), `domainImport` (спецификатор импорта домена из прикладного слоя; не задан — относительный путь). По умолчанию — `src/domain/{m}`, `src/app/{m}`. Заготовку пакета модуля (`package.json`, `tsconfig`) пакет не создаёт: `gen` пишет только исходники; workspace — забота проекта.

## Чек-лист выноса (после релиза u7-school)

Состояние на 2026-10-26: имя `dmg-core` на npm свободно; `extract:check` (копия → `check` → `e2e`) зелёный.

1. Проверить, что имя `dmg-core` всё ещё свободно (`npm view dmg-core` → 404); иначе — scope `@<аккаунт>/dmg-core` и замена спецификатора в проекте одним скриптом.
2. Репозиторий: содержимое `packages/dmg-core` с историей (`git subtree split --prefix=packages/dmg-core`); поле `repository` в `package.json`.
3. CI: `bun install` → `bun run check` → `bun run e2e`; публикация по тегу `v*` (`npm publish`, токен в секретах CI). Первая версия — `0.1.0`.
4. Монорепо: `"dmg-core": "^0.1.0"` вместо `workspace:*`; удалить `packages/dmg-core`, `scripts/extract-check.sh` и `extract:check` из `check`; пути плагинов в `biome.json` уже `node_modules/dmg-core/…`.
5. Документация проекта: ссылки `packages/dmg-core/docs/…` → `node_modules/dmg-core/docs/…` (`conductor/architecture/*.md`, скилы); `layers.md`, `migration.md`, `tech-stack.md` — платформа как внешняя зависимость.
6. Обновление платформы: правка в репозитории пакета → релиз → `bun update dmg-core` → `dmg-core sync` в проекте.

## Решения, которые обязательны (общие)

- **Схемы (Б-8):** удаляются тесты приёма/отказа полей платформы. Остаются: своя логика схемы (`refine`/`transform`), отказ прежних форм записи, схема state, разбираемая при чтении файла, — одной таблицей «валидно/невалидно» на схему.
- **Паспорта Def (Б-7):** удаляются все. На модуль остаётся **один** тест состава — доменный `domain/src/user/user.module.test.ts:7` (UC, `dependsOn`; если ему чего-то не хватает — «переписать»).
- **Тексты `label`/`denyMessage` ошибок** не тестируются (TST-09). Одиночные `expect` на них внутри полезных тестов — раздел «Остающиеся проверки `label`» (файл:строка `expect`); снимаются в этом же срезе.
- **Одно правило на двух уровнях (Б-1):** правило проверяет владелец (Ar / DCS / DQS / Policy домена). У UC модуля остаются: один сквозной сценарий на UC и то, что делает только UC (загрузка, свой `*_NOT_FOUND`, запись в UoW, публикация); Policy-отказ UC — **один** кейс на модуль, не удаление всех.
- **Policy домена:** каждое правило — allowed и denied (`testing.md` §3); «без субъекта — denied» — как в `questionnaire-domain-delete.md`.
- **Бот:** integration — связка слоёв, e2e — пользовательская история. Тесты, красные сейчас из-за `course-dmg` (TR-57 в `conductor/architecture/debt.md`), **не удалять** — «отложить до course-dmg».
- Каждое удаление — только если указано, где покрыто то, что тест мог бы поймать. «Нигде» допустимо только для Б-9/Б-11/Б-12/Б-13 — с одной фразой.
- **Б-13 (мёртвый экспорт):** тест не трогаем — `отложить: удалить с кодом`.
- **Направление Б-1:** удаляется копия **выше** владельца. Доменный тест правила (Ar/DCS/DQS/Policy/rules) нельзя удалять со ссылкой «покрыто UC модуля» — наоборот, удаляется копия в UC. Исключение — доменные тесты Def UC (`domain/src/user/**/uc/*.test.ts`): это паспорта/схемы (Б-7/Б-8), поведение держит модуль.
- Ссылка «где покрыто» в другой уровень ведёт только на тест, который инвентаризация того уровня (`user-app.md` §4) считает полезным. Проверяй каждый путь.
- Новые Н-ID инвентаризации в таблице записывай как `Н<n>-domain` (у каждого уровня своя нумерация).


## Решения по открытым вопросам `user-dossier-domain.md`

1. **Мёртвые правила `UserPolicy`** — `canRead`, `canEdit`, `isSubscriber`, `isGuest`, `isStudent` orchestrator удалит вместе с кодом. Все их тесты (включая «полезные» `canEdit` `:123`, `:133`, `:138`) — `отложить: удалить с кодом`. `isMentor` живой (вызывается в `canAddRole`/`canRemoveRole`) — его тесты оцениваются как обычно.
2. **`dossier`** — запланированная заготовка модуля (`conductor/roadmap.md`, Релиз 4), **код остаётся**. Кандидаты Б-8/Б-11 в `categories.test.ts` — `удалить` («нигде» с фразой допустимо: платформа / литералы источника). Остаются `categories.test.ts:54`, `:80` и весь `scores.test.ts`.
3. **Кросс-уровневые ссылки** — доменные тесты правил остаются; копии в `modules/user` удаляет таблица `user-app` (не твоя забота).
4. **Пробелы `removeRole`/`setRole`/`hasRole`** — тестов не добавляем; перечисли в итоге одной строкой.
5. **Policy:** у каждого живого правила остаются allowed и denied. Дополнительные роли в той же ветке, которую код не различает, — `удалить` (не `слить` в `it.each`: число кейсов должно сократиться). Роль-специфичный отказ остаётся, только если код различает эту роль (укажи строку `policy.ts`).

Область — `domain/src/user/**/*.test.ts`, `domain/src/dossier/**/*.test.ts`. База: 70 (`cd domain && bun test src/user src/dossier`).

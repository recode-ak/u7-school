# Система задач и уведомлений — Концепция

> v2 (2026-11-15). Концепция продукта и живые контуры решения; не spec. Модуль задач
> ещё не реализован. Архитектура (слои, Def, UC/ER) появится в spec трека на `dmg-core`.

---

## Бизнес-проблема

Бот вырос из «терминала с одним диалогом» в инструмент, где система сама инициирует
общение: предупреждает о бездействии, просит ментора решить судьбу студента, предлагает
анкету после код-ревью. Проактивные сообщения оформлены как обычные экраны с кнопками
(`ProactiveSender.invite`, временный механизм, ФР-6) — отсюда проблемы:

1. **Хаос кнопок при серии сообщений.** Ментор получает несколько «кандидатов на снятие»
   подряд — кнопки пропадают у сообщений в непредсказуемом порядке.
2. **Анонимность действий.** Подтверждение «Снять студента?» без имени — при серии
   непонятно, о ком речь.
3. **Вторжение в текущий флоу.** Студент проходит урок — прилетает сообщение с кнопками.
4. **Потеря дел.** Предложение, на которое не ответили сразу, утонуло в истории чата.
5. **Дорогой выход.** «Покинуть учёбу» доступно только через 5 дней бездействия.

## Бизнес-решение: pull вместо push

Кнопки из проактивных сообщений убираются. Касания бота делятся на три канала:

| Канал | Суть | Кнопки | Жизненный цикл |
|---|---|---|---|
| **Уведомление** | «знай»: факт или предупреждение | нет | доставлена — всё |
| **Задача** | «сделай / реши» | только в списке задач | окно жизни, статусы, напоминания |
| **Возможность меню** | действие без срока («покинуть учёбу») | в хабе «Учеба» | доступна всегда |

Центр — **единый список задач**: «Мои задачи» в меню и `/tasks`. Система не вторгается
в текущий флоу: уведомляет текстом «есть дело — /tasks» (инвариант И3 бота), пользователь
сам решает, когда заняться.

## Ключевые решения

- **Задача — единая сущность.** «Предложение» — способ рождения *опциональной* задачи,
  «вопрос с развилкой» — тоже задача. Два измерения: форма выполнения × обязательность
  (политика напоминаний).
- **Задача — конверт данных, рендерит канал.** Хранит стабильное: вид (`<домен>.<имя>`),
  исполнитель, ключ дедупликации, конверт владельца (идентификаторы), окно, статус.
  Тексты, имена и числа не хранятся — вычисляются при показе из состояния владельца,
  поэтому всегда свежие; адрес доставки и представление в событие не кладутся (D-63).
  Как показать и куда ведёт кнопка — решает канал (бот, позже web, агент — D-79); домен
  задачи Telegram не знает.
- **Завершение по критерию, а не по «Выполнено».** Задача системного вида закрывается
  действием владельца (UC → закрытие) или фактом домена (событие), а не кнопкой «Выполнено»:
  иначе дыра в инварианте (UC не выполнен, а задача закрыта, и наоборот). Исходы:
  выполнена, отказ, истекла, отменена; закрытая задача не удаляется — история для метрик.
- **Быстрые действия.** Задача выполняется флоу либо одной кнопкой из списка («Продолжить»,
  «Снять с учёбы»); опасные действия подтверждаются, с именем в тексте.
- **Память об отказе — у владельца.** Отказ закрывает задачу, а запоминает его
  модуль-владелец, реагируя на событие закрытия (отказ может прийти кнопкой, стандартным
  «Пропустить» или истечением окна — единая точка).
- **Повтор ситуации обновляет задачу** (по ключу дедупликации), а не плодит дубликаты:
  бездействие 7 → 9 дней — та же задача. Повтор доставки события отсекает inbox (D-47).
- **Касания централизованы в модуле задач.** Приглашения в анкеты, напоминания о
  бездействии, анкеты после ревью, дайджест — владелец домена лишь создаёт задачу; уведомление
  «есть дело», окна и напоминания (по расписанию, D-71) — забота модуля задач.
  Рождение системной задачи — реакция (ER) на доменное событие, не правка детектора (Job).

## Сценарий: ментор снимает кандидата с учёбы

1. Job бездействия публикует событие «кандидат на снятие»; ER модуля потоков создаёт
   задачу (ключ — по студенту, исполнитель — ментор, обязательная). Повтор sweep 7 → 9 дней
   обновляет ту же задачу.
2. Модуль задач шлёт ментору текст «Есть дело — /tasks» (без кнопок).
3. Ментор в `/tasks` видит «Кандидат на снятие: имя, N дней» с [Снять с учёбы] / [Оставить];
   текст строится из студента и потока на лету.
4. [Снять] → подтверждение с именем → UC владельца переводит студента в «брошен» и закрывает
   задачу; событие снимает студента с группы и уведомляет его. Задача исчезает из списка.
5. [Оставить] → закрытие с отказом → ER потоков помечает «ментор оставил» → sweep не
   создаёт кандидата повторно до нового повода (возобновление учёбы сбрасывает пометку).

Вариация для студента: «Похоже, вы бросили учёбу» с [Продолжить] / [Покинуть учёбу].
«Продолжить» — осознанный сигнал, сбрасывает каскад предупреждений; «Покинуть» — честный уход
самим студентом, задача ментору не создаётся.

## Manual-задачи («лицом к лицу»)

Ручная задача ментора («проведи сессию ПП со студентом A») — человек создаёт, исполняет
вне системы. Живёт в том же модуле (единый список — продуктовое ядро): тексты автора
персистятся, ключа дедупликации нет, кнопки стандартные [Выполнено] / [Отказаться];
автор может отменить, отказ исполнителя уведомляет автора.

**Фиксация результата** — спектр: (1) развязано (инструкция + ручная анкета); (2) связка
идентификатором задачи в анкете; (3) UI-склейка «после Выполнено — Завести анкету»;
(4) домен-владелец вида, закрывающий задачу только событием «анкета заполнена».
Переходить на 4, когда финал по смыслу — не «провёл», а «создан артефакт-оценка», и его
наличие входит в решения (движение по потоку, дашборды). Модуль задач при этом не меняется.

## Выгоды

- Ниже нагрузка на менторов: честные уходы оформляют сами студенты, каскад обрывается раньше.
- Ничего не теряется: все дела в одном списке со статусами, сроками, напоминаниями.
- Флоу пользователя не прерывается; кнопка готова в задаче — конверсия действия максимальна.
- Прозрачность: висящие дела измеримы (сколько, как долго, у кого).

## Открытые вопросы

1. Политика напоминаний о висящих задачах: частота и тон.
2. Повторные окна после отказа: когда система вправе предложить снова.
3. Дайджест: склеивать пачку новых задач в одно сообщение?
4. Сортировка списка задач: свежесть × приоритет (manual с дедлайном — выше).
5. Брошенная анкета — задача или уведомление (тон продукта).
6. Окно жизни кандидата на снятие: N дней или «до конца бездействия».
7. Проверка прав при закрытии: только исполнитель или владелец домена.

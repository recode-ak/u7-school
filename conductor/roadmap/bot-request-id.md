# Бот: `requestId` из `update_id` — заготовка трека

> **Статус: заготовка, не решение.** Зарегистрирован в [реестре треков](../tracks.md)
> как **кандидат `[?]`** (2026-10-27, после трека command-dispatch). Файл удаляется
> по завершении трека-наследника или при отказе; тогда же снимается запись `[?]`.
> Долг — [DEBT-38](../architecture/debt.md).

## Проблема

`U7BotUiStory.dispatchUc` строит след UC (`Trace.fromRequest`), но `update_id`
Telegram до story не доходит: его видит только `main.ts`, а контракт ядра бота
(`BotUpdate`, `handleCallback`/`handleMessage` в `platform/core/src/ui/bot`) его не
несёт. Поэтому `requestId` создаётся на каждый вызов с `warn` (ERR-07):

- лог засорён `warn` на каждое действие пользователя;
- повторная доставка апдейта даёт новый `requestId` — отсев повторов command UC
  (DEBT-1 пакета `dmg-core`, бывший DEBT-36; `transport.md` §2) для бота работать не будет;
- вызовы UC одного апдейта не связаны в `oplog` общим `correlationId`.

## Варианты

- **A. Протащить через контракт:** `update_id` в `BotUpdate` → `UiApp` → аргумент
  `handle*` (или контекст запроса story). Меняются сигнатуры всех stories.
- **B. Контекст запроса на время обработки:** транспорт кладёт `requestId` в объект
  запроса, который story получает уже сейчас (`session`/резолв), `dispatchUc` берёт
  его оттуда. Сигнатуры не меняются, но появляется неявная зависимость.
- **C. Ждать ui-manifests (D-26):** контракт story переписывается там целиком.

## Критерии готовности

- `dispatchUc` получает `requestId = tg:<update_id>`; повтор апдейта — тот же id.
- `warn` о созданном `requestId` в боте не пишется; DEBT-38 снят.
- Тесты: стори и транспорт (`requestId` доходит), e2e — два вызова UC одного апдейта
  с общим `correlationId`.

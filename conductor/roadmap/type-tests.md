# Тесты типов в `dmg-core` — разбор кандидата

**Назначение:** заготовка трека-кандидата «аудит тестов типов»: какие тесты типов лишние, какие оставить, объём. Закономерность — Б-17 в [test-bloat.md](./test-bloat.md) §2. Решение Нурболата — 2026-11-06, трек `tst-cleanup_20261105`.

---

## 1. Проблема

Тест типа проверяет вывод или запрет на уровне `tsc`. Реальный код, который пользуется типом, тоже проверяется `tsc` в `check`. Поэтому позитивный тест («тип выводится как …») дублирует использование. Негативный («это не компилируется») не дублирует: реальный код запрещённое не пишет, и гарантия держится только на тесте.

## 2. Правило

- **Удалять:** позитивные тесты типов (`expectTypeOf(x).toEqualTypeOf<…>`, `Equal<…>`), если тот же вывод использует рабочий код или пример пакета (`src/testing/example/`).
- **Оставлять:** негативные `@ts-expect-error` на публичные гарантии платформы: вызов Def вне `calls`, ошибка вне Meta, мутация `ReadonlyAr`/`state`, команда чужого модуля. Если тип случайно расширится до `string`/`any`, сломается только такой тест.
- **Позитивный тест на неочевидный вариант**, которым рабочий код не пользуется, но который гарантирует тип, — оставлять.
- **`@ts-expect-error` без пояснения** проходит на любой ошибке компиляции — сузить: пояснение плюс ровно одна ожидаемая ошибка в строке.
- **`@ts-expect-error` ради рантайм-ветки** (неизвестная команда, `as never`) — не тест типа: оценивать как обычный тест.

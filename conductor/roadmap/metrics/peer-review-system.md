# Система отзывов и оценок (peer-review) — видение

**Назначение:** что модуль `peer-review` собирает по мероприятиям школы и на каких решениях строится. Реализован первый этап (отзывы по окну судьбы студента); детали — в коде `domain/src/peer-review`, `modules/peer-review` и spec архивных треков.

> **Родитель:** [Система сбора метрик](./metrics-system.md). **Связан:** [спека UI отзывов](../../../runners/u7-bot/src/controllers/peer-review/ui-spec.md) (экраны S01–S07), модуль `dossier` (агрегация, карта — [roadmap](../../roadmap.md)), [цифровой паспорт](./digital-passport.md) (предъявление), [сессии](../sessions-system.md) (будущий источник кампаний).
>
> Терминология: **модуль** курса — учебная единица программы; **поток** — инстанс модуля для группы; студент проходит модуль через поток.

---

## 1. Видение

По каждому **мероприятию** школы (учёба в потоке, сессия код-ревью, парное программирование) модуль собирает **факты**: кто участвовал, что участники сказали друг о друге (текстовые отзывы) и как оценили (анкеты). Факты — сырьё для досье студента и его цифрового паспорта.

Каркас — **кампания сбора = окно судьбы одного участника (субъекта)**: личное событие субъекта (завершил / покинул) → персональное окно → снапшот его окружения → сбор «по горячим следам». В окне два автора: субъект — о своём окружении, ментор — о субъекте. Отзыв виден всем участникам; анкета — отдельная точка входа («Написать отзыв» / «Заполнить анкету»).

peer-review отвечает на вопрос «**что люди сказали друг о друге?**». Агрегация в досье — `dossier`, предъявление — `passport`, реестр мероприятий — `sessions`. «Досье» закреплено за агрегацией; кампании досье не называются.

## 2. Ключевые решения

1. **Кампания — сбор фактов, не агрегатор.** Хранит снапшот участников, окно, отзывы и (в будущем) анкетные оценки; формул агрегации не содержит — «все цифры по модулю» собирает `dossier` композицией фасадов peer-review, sessions, stream. Отвергнута «агрегирующая кампания модуля с дочерними досье сессий»: к какому модулю относится сессия, знает `sessions`, а не кампания.
2. **Контекст `stream_fate` — «судьба студента в потоке определена».** Триггеры — личные события `student.completed` и `student.abandoned`. Кампания персональная, ключ `(scopeId, subjectId)`: одно окно на участника на поток, открывается сразу по событию. Состав — id адресуемых соучеников (для «завершил» — завершившиеся и ещё учащиеся, для «покинул» — пусто); специфика контекста — в payload. Кампании ментора нет: он пишет о субъекте в кампании субъекта. Каркас общий, контексты расширяются (сессии, курс) без его смены.
3. **Отзыв — запись на пару** (кампания, автор, адресат), перезапись в пределах окна; хранит `direction` (student_student / student_mentor / mentor_student) и снапшот исхода автора. Адресация — правила агрегата кампании: субъект → соученики и ментор, ментор → только субъект, никогда — отзыв о себе; субъект «забросил»/«не начал» пишет только ментору.
4. **Исход субъекта — собственная проекция peer-review** из четырёх значений («завершил и прошёл», «завершил и не прошёл», «забросил», «не начал»); она вычисляется ER через read-API `stream` и выбирает тексты и лейблы. Модуль не копирует чужой словарь: каждый клиент строит ту проекцию, от которой зависит его логика.
5. **Окно жизни хранится** (`expiresAt` от момента события, константы в домене; 7 дней для `stream_fate`), не вычисляется на лету.
6. **Создание кампаний — ER, не UC, через доменную фабрику.** Операция реактивная, UI её не вызывает: одна мультисобытийная реакция даёт идемпотентность по `(scopeId, subjectId)`, сбор состава фасадом `stream`, создание и публикацию `campaign.created` (канон содержательных ER, как в `wish`). UC — только пользовательские операции. Инвариант терминальности потока (завершение требует терминального статуса у каждого студента) гарантирует, что все кампании созданы до его закрытия.
7. **Анкетная фиксация — запись, не движок.** Результат анкеты по мероприятию фиксируется из события завершения анкеты (кто, кого, контекст, баллы); движок остаётся в `questionnaire`.

## 3. Техдолг и развитие

1. **Анкеты в кампании:** кнопка «Заполнить анкету», запуск через фасад `questionnaire` с `ownerInfo` кампании, фиксация результата (решение 7), пулы вопросов по контекстам ([metrics-conception](./metrics-conception.md)). Имя агрегата фиксации и место пулов — при планировании этапа.
2. **Приглашения — задачи.** Доставка приглашений сейчас идёт временным проактивом `invite` (долг [C-DEBT-45](../../debt/code.md)); заменяется задачами модуля `task` ([tasks-system](../tasks-system.md)); домен peer-review не меняется.
3. **Сессионные кампании:** контексты по завершении парного программирования и код-ревью — после `sessions`.

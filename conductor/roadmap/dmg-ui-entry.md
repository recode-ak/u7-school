# Вход для `dmg-ui`

**Назначение:** что будущая spec `dmg-ui` (пакет UI поверх `dmg-core`, D-26, D-79, D-80) обязана учесть: задачи из долга и бэклога, которые решаются только вместе с новым контрактом story, и судьба текущего UI-кода проекта. Это вход, а не план: решения по пунктам принимает spec `dmg-ui`.

---

## 1. Форма ввода по схеме входа UC (wizard)

Сейчас пошаговый ввод написан вручную в единственном мастере — создание потока (`runners/u7-bot/src/controllers/mentor/stories/create-stream.ts`). Отдельный базовый класс `WizardStory` не делаем: `dmg-ui` строит форму из схемы входа UC (поля, валидация, ошибки по `Result`), мастер потока переходит на неё. Тот же механизм — у `dmg-cli` (D-79, п. 2): форму строит граф Def, а не канал.

## 2. Экран отказа по `Result`

`ucErrorScreen` (`runners/u7-bot/src/controllers/questionnaire/stories/render.ts`) дублирует ветки `ucErrorNotify`. Один экран отказа по коду ошибки UC — вместе с контрактом story.

## 3. Сборка UI: каскад `init` vs конструктор

Бэкенд собирает зависимости конструктором (DMG: модуль, UoW, репозитории; `init/start/stop` по слоям закрыт). UI собирается в два шага: объекты создаются без зависимостей, затем `uiApp.init(resolve, transport)` каскадно раздаёт `eventBus`, `appApi`, `uiApp`, `dialogCache` контроллерам и стори (`platform/core/src/ui/{ui-app,ui-controller,ui-story}.ts`, `ui/bot/{ui-app,bot-controller,bot-ui-story}.ts`; порядок — [bot-architecture.md](../architecture/ui/bot-architecture.md) §5). Причина — цикл: транспорту нужен `uiApp`, стори — транспорт и `uiApp` (меню, переходы между контроллерами).

Цена каскада: стори до `init` — полуобъект (поля `!`, проверка «не инициализирован» в рантайме), тесты повторяют двухшаговую сборку. Для spec `dmg-ui`:

- стори объявляется манифестом (`defineStory`, D-26), зависимости получает исполнитель манифеста — по образцу UC в `dmg-core/app`, а не каскадом по дереву объектов;
- цикл транспорт ↔ приложение рвётся портом (транспорт видит узкий интерфейс приёма апдейтов, стори — порт отправки), а не отложенной инициализацией;
- критерий: в коде UI нет `init(resolve)` и полей с `!`, сборка — один проход в `main.ts`.

## 4. Путь данных для экранов `stream` (F-110, D-72)

Решается в spec `dmg-ui`, отдельного трека нет (Нурболат, 2026-11-15): переход до `dmg-ui` переписал бы файлы раннера, которые `dmg-ui` перепишет снова.

**Что сейчас.** Экраны потока читают проекции из query UC:
- `getStudentProgress` (`domain/src/stream/student/uc/get-student-progress.uc.ts`) отдаёт готовую карточку, дерево, прогресс и позицию — 7 файлов раннера;
- `getStreamMembers` (`get-stream-members.uc.ts`) отдаёт `roster`, `neverStarted`, `inProgress` — 4 файла раннера; `peer-review` берёт только `students`;
- типы проекций раздувают `domain/src/stream/contract.ts`.

Оба пути D-72 равноправны: это не долг, а выбор под сценарий. Переход оправдан, если проекции дублируют логику Ar/DQS или ответы растут под каждый экран.

**Для spec `dmg-ui`:**
- разобрать каждый сценарий UI потока: какой путь D-72 дешевле — готовый ответ или `ReadonlyAr` + DQS;
- где «домен на фронте»: контракт `stream` отдаёт `StudentAr` и DQS прогресса (JSDoc «кто и зачем», D-74), query UC сводятся к `StreamView`/`StudentView`, экраны решают вопросами, типы проекций уходят из контракта;
- манифест экрана объявляет, откуда берётся основание решения, — и это видно в графе;
- видимое поведение не меняется; регресс навигации держат e2e `runners/u7-bot/tests/e2e/stream-*`.

## 5. Пакет `@u7-scl/core` (`platform/core`)

Что в нём и куда уходит:

| Подпуть | Содержимое | Потребители | Судьба |
|---|---|---|---|
| `./ui` | `UiApp`/`UiController`/`UiStory`, бот: `U7BotUiApp`, `BotController`, `U7BotUiStory`, сессии и `DialogCache`, `BotRequestContext`, построители ответов; `content-nav`, `pagination`, `UiEventContext` | `runners/u7-bot` (≈130 импортов) | заменяется `dmg-ui`; `content-nav` и `pagination` — проектные рендереры, в `runners/u7-bot` или в манифесты представлений (D-80) |
| `./shared` | `Logger`/`ConsoleLogger`, `MdText` и `md*`, валидатор MarkdownV2, `now`, `serializeError`, `stringUtility` | бот, `platform/app`, `scripts/` (≈80 импортов) | `MdText` и валидатор — в рендер бота `dmg-ui`; логгер и `serializeError` — сверить с `dmg-core/app`; остаток — в `platform/app` или раннер |

Цель (roadmap, п. 4): после `dmg-ui` пакета `@u7-scl/core` нет. Порядок — по контроллерам: эталонный переходит, остальные следуют; пока идёт переход, `./ui` живёт рядом с `dmg-ui`.

## 6. Автоподключение к группе потока

На `student.enrolled` студент попадает в Telegram-группу потока (`telegramGroupId`, ссылка — `telegramGroupInvite`) без ручного перехода по ссылке. Нужна операция транспорта (Bot API: `createChatInviteLink` или `approveChatJoinRequest`) и реакция UI на событие — не отдельным обработчиком в обход story. Сообщение о зачислении уже есть — не дублировать.

## 8. Контракт бота, который `dmg-ui` обязан сохранить

Инварианты bot-ui (разрез — [bot-architecture.md](../architecture/ui/bot-architecture.md)) переходят в `dmg-ui` как требования к контракту story, а не как деталь бота:

- диалог один, ввод и экран принадлежат ему; кнопка валидна ⟺ штамп `seq` совпал (без исключений);
- один живой экран, прошлые гасятся при любой смене («хлебные крошки»);
- проактив (`notify`) не трогает диалог и сессию; кнопочный `invite` (ФР-6) — временный, уходит с модулем задач;
- тексты — только `MdText` (экранирование типом); порядок на чат — per-chat очередь.

## 9. TTL ввода и серия экранов

Ожидание текстового ввода (`awaitInput`) живёт без TTL: `ttlSeconds`/`expiresAt`/`handleTimeout` удалены как мёртвые (ни одна story не задавала). Долгое бездействие обслуживают доменные механизмы (sweep брошенных анкет, задачи-продолжения). Вернуть TTL — неразрушающее расширение контракта, при реальной потребности. Так же не входит в контракт серия экранов подряд (`sendMessages`, нужен `preamble`) — добавляется при необходимости.

## 10. Совместимость с задачами

Модуль задач ([tasks-system.md](./tasks-system.md)) ложится на контракт без изменений: `/tasks` — обычный экран диалога, команда с `delegate` открывает его (stop-ответ команды с `delegate` исполняет ядро); кнопка задачи несёт штамп и ведёт мостом в story владельца (подтверждение → UC → закрытие задачи); устаревшая кнопка отсекается штампом, закрытие идемпотентно. Рендер вида задачи в кнопки — задача канала (бот), не домена. Экраны ошибок получают кнопку выхода от приложения («⬅️ Мои задачи» для списка). После MVP задач `invite` и якорь `app/invite` удаляются.

## 11. Заместитель как актор сторис

Актором сторис может быть заместитель (`DelegateCaller`, D-89 пакета): экран показывает данные замещаемого, а в шапке — что действует заместитель и, при `readOnly`, что изменения недоступны. Отказ `UNAUTHORIZED { reason: 'personal' | 'readOnly' }` — обычный экран отказа (§2), кнопки command UC при `readOnly` лучше не показывать вовсе. Первый потребитель — служебный доступ в боте ([D-DEBT-9](../debt/product.md)).

## 12. Что нужно от `dmg-core`

Перечень по этапам — [roadmap.md](../roadmap.md), «Что нужно от `dmg-core` на каждом этапе». Для spec `dmg-ui`:

- первый срез — трек в `dmg-core`: общий формат графа и `ArchChecker`, принимающие расширения пакета; без него `dmg-ui` не на что опереть;
- строки «сверить» этапа 2 (примитивы манифестов, подписка на события, текст отказа) spec закрывает чтением кода пакета: годится как есть или нужна правка — второй релиз пакета;
- форма по схеме (§1) и генерация документации — этап 3: пилотный контроллер без мастера, превью его экранов живут как snapshot-тесты; `mentor` переходит последним.

## 13. Многоязычность

Требование (Нурболат, 2026-11-15): UI на нескольких языках. Расклад для spec — где что живёт:

- **Тексты экранов** (экраны, кнопки, уведомления) — целиком `dmg-ui`: каталог сообщений по ключу, локаль — в контексте рендера, результат — `MdText` (§8). Примеры манифеста (D-80) рендерятся в каждой локали: превью и snapshot на язык.
- **Тексты контрактов** (`label`/`description` Def, метки полей `F.*`, `denyMessage`, тексты ошибок) остаются в `dmg-core` на одном языке — это язык по умолчанию и язык для PO и LLM. Перевод — каталог на стороне `dmg-ui`, ключ — то, что уже стабильно: FQN Def, `code` ошибки, имя правила (`rule`), имя поля. Перевода нет — берётся текст Def. Касается формы по схеме (§1), экрана отказа (§2), cli-ui и агента (D-79).
- **Домен локаль не знает**: текстов для пользователя он не порождает, транспорт несёт `code`, `kind`, `payload`. В `Caller` и `Trace` локали нет.
- **Локаль пользователя** — предпочтение в его профиле (обычное поле домена проекта); подсказка канала (`language_code` Telegram) — только значение по умолчанию. Уведомление рендерится в локали получателя, а не того, кто вызвал событие.
- **Даты, числа, множественное число** — `Intl` (встроен в Bun), без зависимостей.
- **Сверить в `dmg-core`** (§12): `denyMessage` в payload `ACCESS_DENIED` — готовый текст; хватает ли `rule` как ключа (уникальность имени). Полнота каталога (ключ из графа без перевода) — проверка `ArchChecker` расширением пакета.
- **Не входит:** перевод контента курсов (шаги, уроки) — модель данных проекта, отдельная задача.

# Лишние тесты — каталог боли

**Назначение:** разбор кандидата в трек «чистка тестов»: что считается лишним тестом, по каким признакам его искать и журнал найденных случаев. Правило — TST-08 и D-66 пакета (`node_modules/dmg-core/docs/reference/testing.md` §5).

---

## 1. Проблема

При рефакторинге функционал не меняется, а число тестов растёт, будто он добавляется. Одно правило проверяется на двух уровнях, тесты медленнее читаются и правятся, а при следующем переносе дубли переносятся снова.

Корень — перенос по умолчанию превращается в копирование: «поведение вызывающего не изменилось — его тесты не трогаем».

## 2. Закономерности

Сводка инвентаризаций `wish` и `stream` (трек `tst-cleanup`, файлы `conductor/tracks/tst-cleanup_20261105/inventory/*.md` в ветке `tst-cleanup`: там признаки grep, примеры и номера З1–З14 по файлам). Кандидатов — 31–62% тестов слоя; больше всего в прикладном слое (UC повторяет домен).

Вопрос к тесту: **«какая реальная ошибка в коде модуля уронит этот тест и только его?»** Нет такой — кандидат.

**А. Одно правило — несколько мест**

| ID | Закономерность | Признак | Как появляется |
|---|---|---|---|
| Б-1 | Правило проверено уровнем ниже и повторено выше (UC ↔ Ar/DQS/Policy, story ↔ резолвер) | `it` UC без загрузки, Policy, своей ошибки, записи в UoW | перенос 1:1, вынос логики вниз |
| Б-2 | Вопрос Ar проверен своим `it` и через единственного потребителя | метод Ar с одним вызывающим, тест вызывающего ловит инверсию | перенос `a-root.test.ts` 1:1 |
| Б-3 | Общий хелпер проверен в каждом вызывающем | одинаковое тело `it` в нескольких файлах раздела | хелпер выделен, тесты-копии остались |
| Б-4 | Integration/e2e дословно повторяет unit-тест story | совпадают имена `test(...)` и строки экрана | интеграционные файлы legacy-эпохи, e2e копированием |
| Б-5 | Файл-двойник после переезда (старый файл тестов не удалён, или «новое поле» — новым файлом) | `*.student.test.ts`, `*.roster.test.ts`, «Заменяет ожидания…» | «чтобы не ломать старый» |
| Б-6 | Копия соседнего теста без нового класса входа; строка таблицы конфигурации — отдельным `it` | `it.each` по параметру, который код не читает; по `it` на шаг одного обработчика | TDD по шагам до свёртки в таблицу |

**Б. Проверяется не код модуля**

| ID | Закономерность | Признак | Как появляется |
|---|---|---|---|
| Б-7 | Ручной паспорт Def — дубль `arch:check` (состав `errors`/`emits`/`calls`, реэкспорт ключами) | `normalize(`, `ArchChecker` в тестах модуля | эталон `wish` задал образец, скопирован |
| Б-8 | Схема платформы: приём/отказ `F.uuid`, `picklist`, `variant`, `expectedVersion` | `safeParse`/`v.parse` на Def-схемах | правило `testing.md` §3 «Схемы — все поля» |
| Б-9 | Поведение платформы: `UNAUTHORIZED`, `VersionConflict`, изоляция Job, умолчания story бота, «событий нет» отдельным `it` | `menuButtons` пусто, «Неизвестная команда», `published).toEqual([])` | привычка «на каждый UC/story — свой набор» |
| Б-10 | Тест фейка, стаба или фикстуры (фильтр выборки делает фейк; «поток засеялся») | «чужие записи не затронуты», id фикстур | перенос фильтрации в репозиторий без переноса теста |

**В. Тест не может упасть**

| ID | Закономерность | Признак | Как появляется |
|---|---|---|---|
| Б-11 | Тавтология: константа ↔ та же константа, ожидание посчитано тем же продовым кодом, однострочный геттер | `const expected = new <ProdClass>`, FQN/код ↔ свой литерал | «удобно не писать числа» |
| Б-12 | Пустой вход → пустой результат на `filter/map` | «… нет — пусто» | перенос таблицы границ из legacy |
| Б-13 | Тест мёртвого экспорта — сигнал удалить код, а не только тест | экспорт без импортов вне своего теста | legacy-фасад, «на всякий случай» |

**Корни.** (1) Перенос копирует тесты вместе с кодом; (2) тесты первого шага TDD (схема, паспорт) остаются как «контракт»; (3) образец эталона размножается копированием; (4) правило «Схемы — все поля» само порождает Б-8; (5) нет правила «один сценарий — один файл».

Новый случай — новой строкой; подробности — в журнал.

## 4. Как пополнять

- Ревьюер и авторы пишут в отчёте строку «Кандидат в чистку тестов: файл — что дублирует» (роль `dmg-reviewer`); orchestrator переносит её в журнал.
- Случай с новым признаком — строка в §2; если из него следует правило — правка `testing.md` пакета или проектного документа и ссылка оттуда.
- Дубли в коде текущего среза чистятся в срезе (TST-08); сюда — для учёта. Накопленное до правила — ждёт трека.

## 5. Трек чистки

Трек `tst-cleanup_20261105` (ветка `tst-cleanup`): Ф1 — закономерности §2 на `wish`/`stream`; Ф2 — чистка `wish`, `stream`, `questionnaire`, `peer-review`, `user`, `dossier`. Для каждого удаления — «удалён → закономерность → где покрыт»; критерий — число тестов падает, покрытие строк не падает, `check` зелёный.

## 6. Рекомендации для `course`

`course` в трек чистки не входит: его меняет `course-dmg`. Замер признаков (2026-11-05): `normalize`/`ArchChecker` — 17 тестовых файлов (Б-7), `safeParse`/`v.parse` — 174 вызова (Б-8), legacy-тесты `modules/course/src/api` — 21 файл, тесты бота по курсу — 13 файлов.

- **Профилактика в `course-dmg` Ф4–Ф5.** При переводе тестов бота на Def-имена не переносить Б-4 и Б-9: integration/e2e каталога и навигации — один сквозной сценарий на файл, умолчания платформы story не повторять. Legacy-тесты `api/**` удалять вместе с кодом (журнал), не переносить.
- **После Ф5 — отдельный трек** по схеме `tst-cleanup`: инвентаризация по слоям (домен, модуль, бот) на flash с промптом `inventory/prompt-*.md`, затем таблицы удаления.
- **Порядок:** Б-7 и Б-8 (механически, большой объём) → Б-1/Б-2 (UC ↔ DQS, уже частично почищено в треке) → бот (Б-4, Б-9) после зелёной базовой линии `test:bot`.
- **Не трогать:** строгое чтение `courses.json` (инвариант программы при чтении — защита данных), тесты этапов-меток (курс без этапов / один / несколько).

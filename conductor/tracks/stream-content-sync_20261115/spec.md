# Spec: обновление контента идущего потока (F-80)

## Обзор

Автор правит опубликованный модуль, идущие потоки живут на замороженном снимке (`contentSnapshot`). Фича даёт ментору потока (или админу) привести поток к текущей опубликованной версии модуля — безопасно для прогресса студентов: **предпросмотр** изменений по классам и по студентам → **подтверждение** → **применение** одной операцией UoW. Фича не зависит от того, как автор правил модуль: сравниваются снимок потока и свежий `getModuleSnapshot`.

Заменяет временные скрипты `scripts/update-stream-snapshot.ts` и `scripts/stream-snapshot-sync.ts` (их поведение — ориентир, не требование). Источник — F-80 (`revision-release_20261112`), D-85; заготовка — `conductor/roadmap/stream-snapshot-dmg.md`.

## Функциональные требования

- **ФР-1. Допустимость по статусу потока:**
  - `enrollment` — полная замена снимка, анализа студентов не нужно;
  - `active` — замена по правилам ФР-3…ФР-5;
  - `completed`, `archived` — отказ (снимок — история пройденного).
- **ФР-2. Классы изменений** — доменное правило (DCS потока и студентов) сравнивает старый и новый снимок **по позициям шагов**, а не по множествам id (перестановка тоже учитывается):
  - только заголовки проектов/уроков;
  - добавленные или переставленные шаги — для каждого активного студента (`enrolled`, `active` — `StudentAr.isInProgress()`): впереди его текущего шага / в хвосте / позади — по позиции текущего шага в **новом** снимке;
  - удалённые шаги — пройденные студентом / текущий шаг студента.
- **ФР-3. Шаг оказался позади студента** (добавлен, переставлен, перенесён в другой урок или проект) — операция `StudentAr` засчитывает его задним числом **с пометкой «зачтён синхронизацией»** в записи шага; без событий прогресса (реакции не срабатывают); повтор — без изменений.
- **ФР-4. Удалён текущий шаг студента** — отказ всего обновления; в отчёте — какие студенты стоят на удаляемых шагах. Записи о пройденных удалённых шагах остаются в истории студента.
- **ФР-5. Шаг впереди или в хвосте** — студента не трогаем (хвост выдаст существующий `issueTail`). **Намеренное изменение поведения:** студенту, завершившему последний шаг, шаг, добавленный в конец, не засчитывается (старый скрипт засчитывал) — его выдаст `issueTail` при следующем действии студента (Нурболат, 2026-11-15). Пройденный шаг, ушедший вперёд от студента, — предупреждение в предпросмотре, не отказ ([D-DEBT-7](../../debt/product.md)).
- **ФР-5а. Студент `enrolled` без шагов** (в потоке `active` — рассогласование данных или запуск без первого шага) не анализируется и не блокирует обновление; в потоке `enrollment` устаревший указатель первого шага поправит запуск потока.
- **ФР-6. Терминальные студенты** (`advanced`, `not_advanced`, `abandoned`; уход по своей воле — тоже `abandoned`) не затрагиваются и не блокируют обновление. **Намеренное изменение поведения:** старый скрипт засчитывал шаги `advanced`/`not_advanced`; теперь — нет.
- **ФР-6а. Зачтённые синхронизацией шаги** считаются пройденными в прогрессе и дереве урока, но исключаются из статистики времени прохождения (длительность шага `durationOf` — и `computeStepTimeStats`, и медиана/категория `computeAvgTime`) и из «последней активности» студента (`lastActivityAt`, `neverStarted`): зачёт — не работа студента, уведомления о бездействии и отставание от него не сдвигаются (Нурболат, 2026-11-15).
- **ФР-7. Предпросмотр — query UC:** отчёт «было → стало» (проекты, уроки, шаги), изменённые заголовки, затронутые студенты и что с каждым будет, причины отказа (если применить нельзя). Ничего не пишет.
- **ФР-8. Применение — command UC:** вызывают ментор потока или админ (`callers: ['user']`, Policy потока). Поток и студенты — одна операция UoW со сверкой `version`, всё или ничего; запись в лог операций (D-73). Применение не доверяет старому предпросмотру — перечитывает снимок модуля и студентов и проверяет заново. Подтверждение — список затронутых студентов, которых ментор видел в предпросмотре: если при применении набор затронутых другой (кто-то продвинулся) — отказ «перепроверь»; без подтверждения при наличии затронутых — отказ.
- **ФР-8а. Порядок записи.** UoW `dmg-core` пишет агрегаты по очереди без отката (JSON-хранилище не атомарно). Версия потока сверяется до записи; студенты пишутся первыми, поток — последним. При сбое посередине снимок потока остаётся старым, частичный зачёт безвреден, а повторный запуск (зачёт идемпотентен) доводит обновление до конца. Транзакция в платформе — за рамками.
- **ФР-9. Временный вход — скрипт админа** `scripts/update-stream-snapshot.ts`: вызов UC через сборку `U7App` (`dispatch`) от субъекта; выбор потока → предпросмотр → подтверждение → применение; `--dry-run` — только предпросмотр. `stream-snapshot-sync.ts` удаляется, тесты переезжают в домен (TST-08).
- **ФР-10. Студентов не уведомляем.**

## Нефункциональные требования

- Домен чистый и синхронный, без новых зависимостей; TDD (red-тесты по Def до реализации).
- Совместимость: живые `streams.json`/`students.json` читаются без миграции; новое поле-пометка в записи шага — необязательное. Проверяет `dmg-data-keeper`.
- Проверка — только сухой прогон на копии `data/`; запись в живые `data/` — по протоколу AGENTS.md.

## Критерии приёмки

1. Тесты домена покрывают все классы ФР-2, включая перестановку шага позади студента и перенос шага в другой урок.
2. Применение к `completed`/`archived` — отказ; удалён текущий шаг студента — отказ без записи, в отчёте студенты.
3. Шаг позади студента засчитан с пометкой, событий прогресса нет, повторное применение — без изменений.
4. Терминальные студенты не изменены.
5. Конфликт `version` потока — отказ до записи; сбой посередине оставляет старый снимок потока, повторный запуск доводит обновление (тест). Без подтверждения или с устаревшим списком затронутых — отказ.
6. Не ментор потока и не админ — отказ Policy.
7. В `data/oplog/` после применения — запись с `writes`.
8. В `scripts/` нет прямой записи `streams.json`/`students.json`; `stream-snapshot-sync.ts` удалён; таблица переноса его сценариев (перенесён / заменён новой логикой / отпал и почему) — в `summary.md`.
8а. Зачтённые шаги не попадают в статистику времени прохождения (тест `StudentProgressDqs`, вкл. медиану) и в последнюю активность студента (тест `StudentAr`).
9. Отчёт `dmg-data-keeper`: живые данные читаются; сухой прогон на копии `data/` выполнен.
10. `bun run check` зелёный, тестов не меньше базовой линии за вычетом перенесённых.

## За рамками

- Экран в боте для ментора — будущий `dmg-ui`.
- Долг студента — пройти пропущенный шаг.
- Перевод студента с удалённого шага на следующий.
- Fork модуля (новый id, история модулей) и операции автора.
- Уведомления студентов.
- Транзакция или откат в UoW `dmg-core`.
- F-111 — во вход ему записывается пример: замена снимка как крупный патч.

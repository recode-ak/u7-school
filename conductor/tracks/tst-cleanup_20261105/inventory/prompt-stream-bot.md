## Как оценивать каждый `it`/`test`

Для каждого задай вопрос: **«какая реальная ошибка в коде модуля уронит этот тест и только его?»** Если такой ошибки нет или её ловит другой тест — тест кандидат.

Подсказки (не ограничивайся ими, ищи новые):
- то же правило на другом уровне (известный случай);
- тест проверяет поведение платформы `dmg-core` (схема valibot, wiring `UseCaseFromDef`, диспетчер), а не код модуля;
- тавтология: проверяет значение, которое сам же положил в фикстуру/мок;
- проверка формы/наличия поля, которую уже гарантирует тип TypeScript или схема;
- тест фейка, а не кода;
- копия соседнего теста с другими данными без нового класса входа (кандидат на объединение);
- integration/e2e повторяет сценарий story- или UC-теста без нового риска (связки слоёв);
- тест без содержательного `expect` (только «не падает»);
- тест текста/константы, где ошибка невозможна или безвредна;
- тест legacy-кода, у которого есть замена на Def.

## Результат

Создай файл `conductor/tracks/tst-cleanup_20261105/inventory/stream-bot.md` (только его, больше ничего не создавай и не меняй):

1. **Сводка** — число тестов по файлам и оценкам.
2. **Закономерности** — главное. Для каждой: название; признак, по которому её искать grep'ом или чтением; почему тест бесполезен; 2–4 примера `путь:строка`; сколько всего случаев; как появляется (при переносе, при написании нового кода, копированием…); что делать (удалить / объединить / переписать).
3. **Кандидаты** — таблица только по тестам с оценкой «сомнителен» или «пуст»: `путь:строка` | имя теста | закономерность | где покрыто (`путь:строка` или «нигде») | что делать.
4. **Полезные тесты** — не перечисляй поштучно; одной строкой на файл: «файл — N тестов, полезны, защищают …».

Будь строгим, но честным: если сомневаешься, ставь «полезен». Таблица кандидатов должна быть проверяемой — каждая ссылка «где покрыто» указывает на конкретный `it`.

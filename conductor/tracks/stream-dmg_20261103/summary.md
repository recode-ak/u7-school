## A/B исполнителей, Ф2 (2026-11-04)

Срез `student` выполнен дважды от одного коммита `d616f12` и одного брифа (`tech-lead`, Opus): **B** — роли через `pi` на DeepSeek (ветка `ab/student-deepseek`), **A** — роли Claude, Sonnet по умолчанию ролей (ветка `ab/student-claude`). Оркестратор — Opus в обеих. Промпты шагов одинаковые; доработки — по одной схеме (дефекты тестов → `test-designer`, остальное → `migrator`). Ревью — слепое: два `reviewer` на Opus, ветки под нейтральными именами. Деньги Claude — эквивалент по ценам API (Opus $4/$20, Sonnet $2/$10, чтение кэша $0.20, запись — TTL 1 ч); фактически это лимит подписки.

Главные `error` B: кнопка «Записаться» осталась на роли `STUDENT` (регрессия UI), пропал текст отказа по пререквизиту с названием модуля, не снят `STUDENT_ROLE_MISMATCH`. У A — только последний (общий промах обеих веток). У A — правки за границами без эскалации (`runJob` в `platform/core`, экспорт в контракт).

**Что выяснилось по ходу:**
- Расширение `pi-dcp` (dynamic context pruning) ломает префиксный кэш DeepSeek: попадание падает до 3–30%, цена хода вырастает в 20–100 раз. С `--no-extensions` и потолком контекста ~150k (`compaction.reserveTokens: 850000`) — 97–99% кэша и ≈$0.001 за ход.
- `deepseek-v4-pro` ≈ ×3.7 к flash за ход; на одинаковой задаче (`data-keeper`) — те же вердикты, чуть аккуратнее в выводах. Два параллельных `pi` с pro зависают.
- Обе модели одинаково пропустили одно поручение брифа шага 1 (перевод legacy-публикаций) — причина в постановке, не в модели.

# Spec: dmg-docs_20261029

## Обзор

В `dmg-core` комментарии в коде заменяют недостающую документацию «как устроено»: JSDoc на 15–20 строк описывает порядок записи, сбои и потоки, которых нет в `docs/`. Трек вводит правило о комментариях, добавляет документацию «как устроено и почему», разделяет `docs/` по типам, сокращает JSDoc до контракта юнита и заводит сопровождение актуальности. Поведение кода не меняется.

Базовая линия (оценка 2026-10-29, `dmg-core/src`, регулярки, не точный замер): 198 файлов, 16 тыс. строк, 16% комментариев, 15 блоков ≥12 строк, 203 строки комментариев со ссылками `D-NN`. Точный замер — в Фазе 0.

Документация u7-school — отдельный кандидат (см. `tracks.md`): там другой подход (`architecture/docs-strategy.md`: манифесты, генерируемая документация).

## Функциональные требования

**ФР-1. Правило о комментариях.**
- Новый ID в `rules.md` пакета. Комментарий допустим, если из кода и типов нельзя вывести: порядок и побочный эффект; причину выбора; единицы и допущения; отклонение от правила с его ID.
- Недопустимо: пересказ сигнатуры, перечень параметров, ссылки на треки (`TR-NN`), «временная реализация». Ссылка на решение — одна `D-NN`, в шапке юнита, не в середине фразы.
- Правило и критерий — в промптах `domain-author`, `api-author` (`dmg-core/agents/roles`), в проектных `migrator`, `tech-lead` (`.agents-core/roles`) и в проверках `reviewer`; `agents:sync`.
- Согласовано с `conductor/architecture/docs-strategy.md` §6.

**ФР-2. Структура `docs/`.**
- Типы: `concepts/` (как устроено и почему), `guides/` (как сделать), `reference/` (rules, naming, typescript, коды ошибок), `decisions.md`.
- `docs/index.md` — вход для человека и раздел «Как устроена документация»: типы, ответственность каждого, направление ссылок, кто и когда актуализирует. `llms.txt` — вход для агента: reference и guides, concepts по требованию.
- Ссылки в одну сторону: concepts → guides, reference, decisions; guides → правила по ID и concepts; reference → только `D-NN`.
- Тест ссылок: все ссылки между файлами `docs/`, из `llms.txt` и из JSDoc (`@see`) — в стиле `debt-check`, в `bun run check`.
- Решение `D-NN` в `decisions.md`: структура, ответственность типов, критерий «оправдан».

**ФР-3. Concepts, 4 документа** по 30–100 строк, схема в mermaid, без перечня полей: «Путь вызова UC» (sequence), «Слои и зависимости», «Жизненный цикл агрегата и событий» (state → Ar → commit → outbox → reaction), «Как читать модуль». Критерий: документ отвечает на вопрос новичка. Во front-matter — `covers:` (пути исходников, которые он описывает).

**ФР-4. Нарезка существующих docs.** Файлы со смешанным содержанием (`transport`, `errors-result`, `layers`, `caller`, `domain-modeling`, `manifests`, `testing`) делятся на нормативную часть (reference) и объяснение (concepts); каждый факт — в одном месте. Ссылки обновлены в `llms.txt`, `rules.md`, гайдах, скилах и u7-school (`AGENTS.md`, `dmg:sync`).

**ФР-5. Стрижка JSDoc в `src/`.**
- JSDoc сокращён до контракта, до 6 строк; больше — со ссылкой на документ или тест.
- Сценарии сбоев (`UnitOfWork.commit`, `CommandReplay`, `REQUEST_CONFLICT`) покрыты именованными тестами; проза про сбои убрана, выжимка — в concepts.
- `D-NN` из середины фраз убраны. Комментарии `cli/scaffold/app-sources.ts` перенесены в шаблоны.

**ФР-6. Сопровождение актуальности.**
- Кто: автор среза обновляет затронутый документ в том же срезе, до гейта; `reviewer` проверяет. Отдельный агент-владелец документов не нужен: он не знает контекста изменения.
- Куда писать: `covers:` (пути исходников) во front-matter у concepts **и guides**; команда `docs:impact <пути>` выдаёт документы, чьи `covers` совпали. Бриф среза, трогающего `dmg-core`, содержит строку «Документы» (заполняет `tech-lead` по `docs:impact`).
- Что писать: таблица в `docs/index.md` — изменилось правило → reference с ID; новый способ делать → guides; изменился поток или жизненный цикл → concepts; изменился контракт или компромисс → `D-NN`. Совпадение `covers` — документ обновляется или в отчёте reviewer явно: «не затронуто, потому что…».
- Механически: `agent-gate.ts` — предупреждение, если diff правит `dmg-core/src/{app,kernel,domain}` без изменений `docs/` и `decisions.md`; проверка `covers:` в `bun run check` — `warn` со списком документов, чьи исходники менялись позже документа; в гейте релиза (`RELEASING.md`) блокирует (по образцу `docs-strategy.md` §3). Ограничения: `covers` знает только записанное; правки форматирования дают шум — при заметном шуме `warn` сужается.
- Аудит: пилот роли `documentarian` (`agent-roles.md`: «документы сходятся с кодом», только чтение, список расхождений) — вызывается после фазы, менявшей документы пакета, и перед релизом. Роль рождается в `.agents-core/roles/`; решение о переносе в пакет — отдельно, с Нурболатом.

## Нефункциональные требования

- `bun run check` и `bun run e2e` пакета зелёные после каждой фазы; изменений поведения нет.
- TDD для кода (тест ссылок, проверка `covers`): red → green.
- Правки пакета — коммит в `~/dev/tools/dmg/dmg-core`, SHA — в коммите u7-school. `data/` не трогаем; без пушей и деплоя.
- Правка документов, доставляемых `dmg-core sync`, — через репо пакета, не в `node_modules`.

## Критерии приёмки

- ФР-1…ФР-6 выполнены; четыре concepts написаны; `docs/` разделён по типам, ссылки проверяются тестом.
- Блоков JSDoc длиннее 6 строк без ссылки нет; доля комментариев и число блоков ≥12 строк снижены относительно замера Фазы 0.
- Сценарии сбоев `commit` и `CommandReplay` покрыты тестами.
- `documentarian` отработал минимум один раз; запись в разделе «Пилот ролей» `summary.md`.

- Генерация доменной документации, `dmg-ui`, рефакторинг кода.

# Спецификация: dmg-core-extract — платформа DMG как внешний пакет `dmg-core`

## Обзор

Трек #1б из [migration.md](../../architecture/migration.md) (после [core-dmg](../../archive/core-dmg_20261018/spec.md)). Платформа DMG (`packages/core/src/dmg`) становится самостоятельным пакетом **`dmg-core`** (npm), который можно вынести в отдельный репозиторий и ставить как внешнюю зависимость. Параллельно закрепляется готовность модулей к выносу в отдельные репо и сервисы ([D-28](../../architecture/decisions.md)).

## Решения

- **Выносим только DMG, legacy остаётся.** Legacy-часть `@u7-scl/core` (`domain/api/ui/shared/infra`) исчезнет вместе с переходом ([legacy.md](../../architecture/legacy.md) §6) и в `dmg-core` не попадает.
- **Мосты к legacy — на стороне монорепо.** 6 файлов `dmg/app/**/legacy-*`, `run-logged`, часть `use-case-from-def` и `context` зависят от `#*-legacy`. Они уезжают в `@u7-scl/core` (подпуть `legacy-bridge`) и зависят от `dmg-core`, не наоборот. `dmg-core` не знает о legacy.
- **Установка — из npm по semver.** До первой публикации и в разработке — workspace-пакет `packages/dmg-core` плюс проверка `bun pm pack` в чистом каталоге. Никаких git-зависимостей и `bun link`.
- **Алиас внутри пакета — `#core/*`** (вместо `#dmg/*`), так как после выноса `src/dmg` станет `src`. Переименование — одним скриптом.
- Имя `dmg-core` свободно на npm (проверить перед публикацией).

## Порядок относительно других треков

Трек делится на две части с паузой между ними; на этот раздел ссылаются планы соседних треков (`generators`, `domain-package`, `golden-wish`).

1. **Часть А — Фазы 1–3** (развязка, пакет `dmg-core`, самодостаточность). Выполняется **до** `generators`. После Фазы 3 путь пакета (`packages/dmg-core`), имя импорта (`dmg-core`, `dmg-core/testing`) и алиас `#core/*` **финальные**: генераторы и эталонный модуль пишутся на них без переименований.
2. **Пауза.** После контрольной точки Фазы 3 трек остаётся открытым (`tracks.md`: `[~]`), работа переходит к `generators`, затем `domain-package` и `golden-wish` ([migration.md](../../architecture/migration.md) §2).
3. **Часть Б — Фазы 4–6** (готовность к распределённому запуску, документация и инструменты в пакете, вынос и публикация). Стартует **после** `golden-wish`: контракты `domain/<m>/contract` требуют `domain-package`; outbox и идемпотентность реакций проверяются на реальном модуле; гайды Фазы 5 пишутся по эталону.

**Что гарантирует часть А соседним трекам:** `dmg-core` не импортирует legacy и `@u7-scl/*` (ARC-10); legacy-мост `packages/core/src/legacy-bridge` остаётся рабочим для `wish`, пока тот на legacy-шине и legacy-`Job`; `bun run check` включает `extract-check`.

**Что соседние треки не делают:** не меняют публичную поверхность `dmg-core` без записи в этом треке; не удаляют `legacy-bridge` до конца миграции.

## Функциональные требования

**Ф1. Развязка.** `dmg-core` без импортов из `*-legacy` и `@u7-scl/*`; правило проверяется `arch:check`/biome. Единственные внешние зависимости — `valibot`, `@valibot/to-json-schema` (peer).

**Ф2. Пакет.** `packages/dmg-core`: `name: dmg-core`, не `private`, `exports` (корень, `testing`, `arch`), `files`, `engines`, `sideEffects: false`. Тестовое (`bun:test`) — только в подпути `testing`. Корневые `paths` убраны, потребители подключают пакет как обычную зависимость.

**Ф3. Самодостаточность.** Свои `tsconfig`, `biome.json`, скрипты `check`. Скрипт `scripts/extract-check.sh` копирует пакет в пустой каталог, ставит зависимости и гоняет `check`; входит в `check` монорепо.

**Ф4. Готовность к распределённому запуску** (закрепляется тестами, а не только текстом):
- Реакции идемпотентны; публикация событий — через outbox-порт (интерфейс в `dmg-core`, реализация потребителя).
- Один UoW — один модуль; межмодульные изменения только через фасад/событие.
- `Caller`, `Trace`, конверт события и снапшот Ar проходят круг через JSON без потерь (тест).
- Контракты модуля (фасад, события, ошибки) выделяются из единого `@u7-scl/domain` отдельным подпутём `domain/<m>/contract`, чтобы зависимый модуль в другом репо брал только их.

**Ф5. Вынос и публикация.** Репозиторий `dmg-core`, CI (check + публикация по тегу), перевод монорепо на версию из npm, удаление `packages/dmg-core` из монорепо; legacy-мост остаётся в `@u7-scl/core`.

**Ф6. Документация и инструменты в пакете.** Главная цель: потребитель `dmg-core` получает полный комплект для разработчика и агента. В пакет входят:
- `docs/` — документация платформы (манифесты, ошибки и `Result`, `Caller`, тестирование, моделирование домена, TypeScript, нейминг, слои, каталог правил с ID) и `llms.txt` — индекс для LLM;
- `skills/dmg-architecture` — как писать модуль на DMG;
- `agents/` — роли `domain-author`, `api-author`, `reviewer` для Claude Code и pi (из `.agents-core/roles`);
- CLI `dmg-core init` / `sync` / `sync --check` — доставка скилов и ролей в проект потребителя и контроль их актуальности по версии.

В проекте остаётся специфичное: `legacy.md`, `migration.md`, `agents.md` (процесс), conductor-скилы, `migrator`, решения по данным. Источник правды по платформе — один, в репозитории пакета.

# Видение: система манифестов

**Назначение:** общая картина после перехода на DMG — куда растут манифесты за пределы домена: UI, документация продукта, развёртывание, системы. Решения — D-78…D-83 ([decisions.md](./decisions.md)); детали UI — [ui-manifests.md](./ui-manifests.md), документации — [docs-strategy.md](./docs-strategy.md).

> Статус: **концепция** (Нурболат, 2026-11-14). API фиксируется на эталонных срезах; реализовано только доменное ядро (`dmg-core`).

---

## 1. Цель

Пишется в одном месте — полезно во многих: манифест даёт **типы** в коде, **проверяемый контракт** в рантайме и тестах, **узлы графа** для документации и инструментов. Человек (программист, аналитик, PO) и агент узнают устройство приложения из графа, а не из кода; граф не может разойтись с кодом, потому что манифест исполняется.

## 2. Один граф системы (D-78)

Слои не строят свои графы — они поставляют узлы и рёбра в общий: узел (`kind`, `id`, `label`, `description`, родитель), ребро (`kind`, `from`, `to`). Один `graph.json`, один инструмент запросов, один просмотрщик.

| Слой | Узлы | Пакет | Состояние |
|---|---|---|---|
| домен | модуль, агрегат, UC, ER, Job, событие, ошибка, правило | `dmg-core` | есть (граф L0–L2) |
| UI | приложение, UI-модуль, сторис, экран, карточка | `dmg-ui` | концепция |
| процессы | процесс, его шаги и ручные переходы | `dmg-core` | концепция |
| развёртывание | юнит (процесс ОС), хранилище, транспорт, окружение | позже | задел |
| масштабы | приложения разных масштабов, их контракты | позже | задел |

Сшивка — по ссылкам на Def: экран → UC → агрегат → событие → реакция → уведомление (экран). Отсюда вопросы, на которые граф отвечает сам: что затронет изменение UC, кто и что увидит при событии, какие UC без UI, что развёрнуто где.

Ядро графа (узел, ребро, регистрация видов) — в `dmg-core/graph`; `dmg-ui` — отдельный пакет в `~/dev/tools/dmg/`, зависит от `dmg-core` и добавляет свои виды узлов.

## 3. UI: три механизма (D-79)

| Тип | Механизм | Манифест |
|---|---|---|
| bot-ui, web-ui | ручные сторис: манифест сторис общий, экраны и рендер — по платформам | матрёшка ([ui-manifests.md](./ui-manifests.md)) |
| cli-ui (терминал, бот) | **генерируется** из графа: форма по схеме входа UC, карточка по схеме выхода (`dmg-cli`; в боте — wizard) | почти нет |
| bot-agent-ui | агент над MCP-транспортом из манифестов (D-18) | список разрешённых UC и ролей |

Унификация — там, где она бесплатна: общие манифест сторис, карточки по схемам домена и автогенерируемый UI. Рендер и навигация платформ не унифицируются. **Агент.** Действует с `Caller` спросившего пользователя — Policy вызывается всегда, отдельной модели прав нет. Query исполняет сразу. Команду только готовит: перечисляет пользователю, что будет сделано, и исполняет после его подтверждения. Несколько команд — один явный перечень и одно подтверждение; отдельное на каждую — когда этого требует логика (следующая зависит от итога предыдущей, действие необратимо).

## 4. Требование живёт в манифесте (D-80)

- В манифесте — то, что нужно почти всегда: `label`, `description` (1–3 предложения), структура (callers, UC, события, переходы) и **именованные примеры** состояний на фикстурах.
- Пример — исполняемое требование: превью рендерит настоящий рендерер, оно же snapshot-тест. `ui-spec.md` удаляются.
- Длинный «смысл» — в соседнем `<имя>.md` (D-27): рядом с кодом, но не в манифесте.
- **Карточка — манифест:** представление схемы домена (выход UC или `view()` агрегата) с примерами и рендерерами по платформам; её берут ручные экраны и автогенерируемый UI. Без фанатизма: экран с одноразовым представлением обходится своим рендером.
- Тексты уведомлений в манифест не пишутся: сторис объявляет `on: Событие` и экран с примером; граф показывает у события, кто получает и что видит.
- Запланированное — в spec трека, в манифест попадает с кодом.

## 5. Документация продукта (D-81)

- **Факты** — детерминированно из графа; **смысл** — моделью, только при смене `defHash`.
- **Агенту** — запросы к графу из CLI (`ls`, `show <id>`, `impact <id>`, `who-calls <id>`), те же данные — MCP resources. В код агент идёт за реализацией, а не за устройством.
- **Человеку** — `docs/domain/` (Markdown), статический сайт и просмотрщик графа из того же `graph.json`.
- **Конечному пользователю** — срез «за кулисами» от экрана: какие операции стоят за действием, при каких условиях оно доступно, какие бывают отказы, кто и что получит. Два среза: «как устроено» — из графа, «что было со мной» — из лога операций (§9). Показываются только узлы с признаком видимости, по умолчанию узел скрыт; текст — пересказ моделью поверх фактов; канал — экран UI или ответ agent-ui. Признак закладывается в формате узла, сам срез — вместе с agent-ui.
- **Модель решений** — порт с тремя вопросами: выбор из вариантов, оценка по шкале, вероятность «да». За ним — Jev (TypeSafe AI; SDK или HTTP — деталь адаптера). Применения: «устарел ли смысл», качество описаний, маршрутизация вопроса в agent-ui. Только сигнал: блокирующие проверки остаются детерминированными.

## 6. Процессы (D-83)

Взгляд на систему не по модулям, а по сквозным сценариям («запуск потока», «сбор отзывов»). Процесс живёт **над модулями** и на платформе ничего не исполняет: работу по-прежнему делают UC, ER и Job, процесс — именованное описание их цепочки.

- **Манифест процесса** — `label`, `description`, участники (роли), начало, исходы и состав: ссылки на Def операций и событий любых модулей. Лежит в домене вне модулей; зависимость направлена от процесса к модулям, как у UI.
- **Операция о процессе не знает.** «В каких процессах участвует UC» вычисляет граф — как все обратные связи DMG. Пометка процесса в Def операции отвергнута: модуль зависел бы от того, что над ним.
- **Рёбра между шагами выводятся** из графа (UC → событие → ER → UC). Объявляются только переходы, которых в коде нет: действие человека (роль и UC) и ожидание времени (Job).
- **Валидность — по слоям:** ссылки на Def — типизация; «от начала до каждого исхода есть путь из выведенных и объявленных переходов» — проверка архитектуры; межмодульная цепочка вне любого процесса — предупреждение; смысл, границы и название — ревьюер.
- Жизненный цикл одного агрегата процессом не дублируется — он в `AggregateDef`.
- Позже: экземпляр процесса восстанавливается из лога операций по следу вызова («где застрял запуск потока»).

## 7. Развёртывание и масштабы (D-82) — только задел

- **Развёртывание** — описательный манифест: юниты, какие приложения и модули в них, хранилища, транспорты. Первая проверка — каждый модуль размещён ровно в одном юните; генерация конфигов — позже.
- **Матрёшка через модуль-владелец.** Единица любого масштаба — приложение на DMG со своим манифестом, модулями, агрегатами, UC, ER, Job, процессами и своей шиной событий. Модуль приложения может владеть **дочерними приложениями**: его UC, ER и Job обращаются к ним через типизированный фасад по опубликованному контракту (как сегодняшние фасады модулей), получая его через резолвер. Внутренние события и фасады дочернего за его границу не выходят — изоляция на каждом уровне.
- **Внутренняя механика `dmg-core` не меняется.** Для приложения-владельца сёстры — обычные модули со своими UC, ER и Job: реакция владельца слушает событие одного модуля и вызывает UC другого, как сегодня. Новое только одно — дочернее приложение у модуля и типизированный доступ к его API через Def UC.
- **Транспорт фасада — деталь развёртывания:** в процессе или удалённо. Одна и та же архитектура собирается монолитом или распределённо.
- **Масштаб задаёт пользователь платформы.** Названия и число уровней — словарь проекта; платформа даёт только вложенность и метку масштаба.
- **Сёстры общаются через родителя:** взаимодействие дочерних приложений идёт в разрезе приложения-владельца — его модулями, реакциями и процессами. Зависимости — сверху вниз: дочернее о родителе не знает и сообщает о себе событиями; взаимная связь возможна, но объявляется явно.
- **Платформенные приложения — вне матрёшки.** Приложение может не входить ни в чей состав и быть доступным с любого масштаба: его фасад получают через резолвер. Какие приложения платформенные — решение проекта.
- **Устройство и работа — разные срезы.** Манифесты описывают типы (как устроено); развёртывание — экземпляры (где и сколько раз запущено) и ссылается на типы. Документация выдаёт оба среза и срез по масштабу; шаг процесса верхнего масштаба раскрывается в процесс нижнего.
- Сейчас закладывается: иерархические `id` узлов, признак публичности UC и событий, контракт приложения, пригодный для фасада, метка масштаба. Остальное — когда появится второе приложение.

## 8. Последовательность

Порядок работ и то, что нужно от `dmg-core` на каждом этапе, — в [roadmap.md](../roadmap.md), раздел «Порядок работ»: хвосты → архитектура `dmg-ui` и пилот → остальные контроллеры → хвосты после UI → новые фичи, web-ui или agent-ui. Из этого документа туда разложено: формат графа — этап 2; генерация документации — этап 3; запросы и diff графа, `dmg-cli` — этап 4; процессы, MCP, HTTP — этап 5, по выбранному направлению.

## 9. Отложено

- **Точный анализ совместимости контракта и гейт** — [D-DEBT-2](../debt/product.md), триггер: перед web-ui. Сейчас — только грубая пометка «возможно ломает» в diff графа.
- **Лог операций поверх графа.** Порядок: отчёт CLI «вызовы, ошибки, длительность по UC за период» → дневные сводки (без входов и выходов — без персональных данных) → слой в просмотрщике → экземпляры процессов по следу вызова → срез конечному пользователю «что было со мной» (только его операции, §5). Сводки и отчёт читают лог через порт: хранилище лога, вероятно, переедет из JSONL в SQL. Не сейчас.
- **Лог UI** («показан экран», «нажато действие») — точка записи закладывается на эталоне `dmg-ui`, сам лог включается позже.

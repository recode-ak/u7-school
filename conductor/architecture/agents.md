# Агентный процесс

**Назначение:** роли агентов, как идёт и проверяется работа, связь с conductor. Среды: Claude Code (основная) и pi (внешний исполнитель) — §8.

---

## 1. Роли

| Роль | Делает | Пишет в |
|---|---|---|
| **orchestrator** (основная сессия с Нурболатом) | декомпозиция, брифы срезов, вызов агентов, гейт, решения, план, коммиты | `conductor/`, коммиты |
| **dmg-domain-author** | state, Ar, Policy, события, ошибки, DCS/DQS, все Def, unit-тесты домена | `domain` |
| **dmg-api-author** | реализации UC/ER/Job, репозитории, фасады, wiring, тесты | `modules/<m>` |
| **migrator** | перевод существующего кода с сохранением поведения | `domain`, `modules/<m>`, точечно вызывающие stories |
| **dmg-reviewer** | проверка по [rules.md](./rules.md), отчёт с ID | только чтение |
| **dmg-tech-lead** | черновик брифа среза по готовой spec: границы, Def, «было → станет», ID правил | только чтение, бриф пишет orchestrator |
| **dmg-test-designer** | характеризация поведения и red-тесты до реализации | `*.test.ts` среза |
| **dmg-data-keeper** | совместимость записей, путь миграции, бэкап | только чтение |
| **documentarian** (пилот) | документы пакета сходятся с кодом: список расхождений после фазы, менявшей документы, и перед релизом пакета | только чтение |
| **dmg-access-auditor** (пилот) | кто может вызвать, нет ли обхода допуска и утечки чужих данных — по diff, затронувшему `Caller`, Policy, допуск UC, ER/Job | только чтение |
| ui-author | позже | — |

Роли `dmg-tech-lead`, `dmg-test-designer`, `dmg-data-keeper` прошли пилот и доставляются пакетом (волна 2 [agent-roles.md](./agent-roles.md) §4); `documentarian` и `dmg-access-auditor` — в пилоте. Там же роли постановки (`dmg-user`, `dmg-ux`, `dmg-product`, `dmg-architect`) и др., пилот и критерии переноса в пакет. Роли людей и правило имён (`dmg-*` — агент, без префикса — человек) — [team-roles.md](./team-roles.md).

**Автор ≠ ревьюер.** Ревьюер не исправляет код. Каждый агент получает минимум инструментов (dmg-reviewer — без write/edit).

## 2. Четыре контура качества

1. **Генераторы** — `bun run gen <kind> …` (`dmg-core gen`, `naming.md` §5 пакета; раскладка — [naming.md](./naming.md)) создают структуру, пары контракт↔реализация, заготовки тестов и правят `index.ts`/`module.ts` по маркерам. Агент заполняет, а не придумывает форму.
2. **Машинный гейт** — `bun run check` + `bun run arch:check`. Запускает **orchestrator сам**, отчёту агента не верит. Хук на завершение субагента в обеих средах гоняет гейт по затронутым пакетам и возвращает ошибки агенту (§8).
3. **Reviewer** — только правила с проверкой `review`, только по diff среза.
4. **Ratchet** — повторяющееся замечание ревьюера → новая машинная проверка → правило в каталоге меняет способ проверки.

## 3. Единица работы — вертикальный срез

Срез = один агрегат со своими UC/ER/Job.

```
orchestrator: задача среза
  → dmg-tech-lead                 → черновик брифа → orchestrator: бриф
  → dmg-test-designer             → характеризация (green) + red по Def
  → dmg-domain-author | migrator  → гейт
  → dmg-api-author    | migrator  → гейт
  → dmg-data-keeper               → отчёт (только по триггеру)
  → dmg-reviewer                  → отчёт
  → orchestrator: решение → правки автором → гейт → коммит
```

- `dmg-tech-lead` — если срез новый или бриф не очевиден; простой срез по готовому образцу orchestrator описывает сам.
- `dmg-test-designer` — до первого автора; автор делает его red-тесты зелёными, тесты не ослабляет.
- `dmg-data-keeper` — если diff затрагивает `state`, `*repo.ts` или снимки.
- Отчёты новых ролей переносятся в бриф, а итог каждого вызова — в `summary.md` трека, раздел «Пилот ролей» ([agent-roles.md](./agent-roles.md) §5).

Параллельно — только срезы независимых модулей (без общего `dependsOn`-пути).

## 4. Связь с conductor

- Conductor остаётся памятью проекта: spec, plan, tracks, архив. Трек = модуль или инфраструктурная задача, фаза = срез, задача = шаг агента.
- **Три уровня постановки** (роли — [agent-roles.md](./agent-roles.md) §3):

  | Документ | Отвечает | Готовит черновик | Когда |
  |---|---|---|---|
  | `spec.md` | что и зачем; доменная модель; устройство | `dmg-user` → `dmg-ux` → `dmg-product`, по триггеру `dmg-architect` (волна 3; до неё — orchestrator с Нурболатом) | `conductor-newtrack` |
  | `plan.md` | нарезка на срезы (фазы) и шаги по ролям (задачи) | `dmg-tech-lead` по spec и коду | `conductor-newtrack`, после утверждения spec |
  | `slices/<срез>.md` | как именно: файлы, Def, «было → станет», ID правил | `dmg-tech-lead` по spec, plan и текущему коду | `conductor-implement`, в начале фазы |

  Брифы не пишутся заранее: предыдущие фазы меняют код. Записывает все три документа orchestrator, spec и plan утверждает Нурболат.
- `conductor-implement` в **режиме оркестратора** (раздел 4.0 скилла): не пишет прод-код, раздаёт задачи, гоняет гейт, отмечает план.
- **Единственный писатель** `plan.md`, `tracks.md` и коммитов — orchestrator. Субагенты не коммитят и не трогают план.
- Субагенты не читают `workflow.md` целиком: в промпт роли входит выжимка и ссылки на нужные документы.

## 5. Артефакты передачи

- **Бриф среза** — `conductor/tracks/<track>/slices/<slice>.md`: границы, список Def и реализаций, сохраняемое поведение (для migrator), критерии приёмки, применимые ID правил.
- **Отчёт автора** — в конце брифа: что сделано, отклонения и почему.
- **Отчёт ревьюера** — там же: `ID | файл:строка | суть | severity`.

## 6. Эталон

Агенты копируют паттерн из образцов двух уровней. **Учебный модуль пакета** `dmg-core` (`node_modules/dmg-core/src/testing/example`) — на каждый вид артефакта гайд в [guides/](../../node_modules/dmg-core/docs/guides/index.md): когда применять, команда генератора, ссылка на образец, чеклист ID, ловушки, как тестировать; ссылки и ID документации пакета проверяет `node_modules/dmg-core/scripts/docs-check.test.ts`. **Эталон проекта** — модуль `wish` (домен `domain/src/wish`, прикладной слой `modules/wish/src`, трек golden-wish): реальные случаи, которых нет в учебном модуле (внешние модули над legacy, мосты, D-41). Роли платформы (`dmg-domain-author`, `dmg-api-author`, `dmg-reviewer`) — в пакете (`node_modules/dmg-core/agents/`), проектное дополнение — `.agents-core/common.md`.

## 7. Условия остановки (эскалация к orchestrator)

- правило противоречит задаче или другому правилу;
- нужно изменить другой модуль или контракт (input/output/errors), от которого зависят чужие вызывающие стороны;
- тесты падают в коде, который агент не трогал;
- любое действие с данными в `data/` — агенты данные не трогают; миграции данных выполняет только orchestrator с подтверждением Нурболата.

## 8. Среды: Claude Code и pi

- **Claude Code — основная.** Субагенты — `.claude/agents/`. Хук `SubagentStop` в `.claude/settings.json` после авторов (не dmg-reviewer) гоняет `scripts/agent-gate.ts`: красный → exit 2, ошибки возвращаются субагенту.
- **pi — внешний исполнитель.** Нурболат включает его сам (кончились лимиты, экономия). Claude Code им не управляет и о его работе узнаёт только из git и conductor. Субагенты — расширение `.pi/extensions/subagent/` (`agentScope: "project"`, модель — `.pi/subagent.json`), агенты — `.pi/agents/`; после субагента расширение вызывает тот же гейт и дописывает результат в ответ.
- **DeepSeek из Claude Code.** Шаг роли можно отдать DeepSeek: orchestrator (Claude Code) запускает роль через `scripts/pi-role.ts` и принимает результат как отчёт субагента. Когда и как — [deepseek.md](./deepseek.md).
- **Гейт по затронутым пакетам** (`scripts/agent-gate.ts`): пакеты из `git status` + транзитивно зависимые → их `check`; корневые конфиги → полный `check`; только `.md` → пропуск. Видит только незакоммиченное.
- **Расширение pi `subagent` — проектное.** Импортирует `scripts/subagent-config.ts` и `scripts/subagent-gate.ts`, гейт — `scripts/agent-gate.ts`: вне u7-school не загружается. Переносимость — только вместе с решением о доставке pi-расширения пакетом `dmg-core` (новый API пакета).
- **Одна активная сессия-оркестратор.** Обе среды не ведут один трек одновременно: правило «единственного писателя» (§4) действует на ту, что сейчас открыта.
- **Передача — через conductor** (протокол — скилл `conductor-implement`, раздел 4.1), обычно на границе фазы или трека. Посреди задачи (исключение) — остановка: коммит (красный `check` — `wip`) и пометка «Передача» под незавершённой задачей в `plan.md`. Старт: `git status`, `plan.md`, `git log` от последнего SHA из плана.
- **Приёмка чужой работы** — как работы субагента: полный `bun run check` и dmg-reviewer по diff, затем продолжение.
- **Один источник текстов.** Скиллы: `.claude/skills` — симлинк на `.pi/skills`. Скил `dmg-architecture` и роли платформы доставляет `bun run dmg:sync` (`dmg-core sync` по `dmg-core.json`): скил — в `.pi/skills/`, роли — в `.agents-core/roles/`, общий блок пакета — `.agents-core/dmg-core-common.md`; `dmg:check` (в `check`) ловит устаревшие и правленые копии. Проектные роли — `.agents-core/roles/` (`migrator` и роли пилота), общий блок проекта — `.agents-core/common.md`; `bun run agents:sync` собирает копии под обе среды, `agents:check` (в `check`) ловит расхождение. Формат — `.agents-core/README.md`.
- Скилл `architecture` — вход в эту папку для основной сессии.
- **Платформа — параллельно.** `dmg-core` (в будущем `dmg-ui`) развивается вместе с u7-school, правка репо пакета — обычная работа трека, не эскалация (изменение контракта пакета — через его `docs/decisions.md`, это стратегическое, §9). Порядок — [index.md](./index.md) §«Правка платформы `dmg-core`»: авторы правят код пакета, orchestrator гоняет `check`/`e2e` пакета и коммитит в его репо отдельно, SHA — в коммите u7-school.

## 9. Режим работы после релиза

С релиза v0.3.0 (2026-11-14) прод работает на живых данных: между фазами система работоспособна, `check` зелёный после каждого коммита. Журнал тактических решений не ведётся.

- **Стратегическое и доменное — с Нурболатом:**
  - форма Def и API `dmg-core`;
  - новые правила `rules.md` и решения `D-NN`;
  - границы модулей и `dependsOn`;
  - соглашения [naming.md](./naming.md);
  - изменение поведения для пользователя;
  - место межмодульного побочного эффекта (вызов фасада, меняющий чужой модуль) — каждый случай отдельно ([decisions.md](./decisions.md) D-41);
  - существенные вопросы предметной области;
  - любые действия с `data/`, теги, push и выкатка.
- **Тактическое и мелкое доменное orchestrator решает сам:** порядок работ, временные адаптеры, замечания dmg-reviewer без `error`, уточнение правила без смены смысла. Решение, несущее знание, — в [decisions.md](./decisions.md) или гайд; временный код — запись `C-DEBT-<n>` ([conductor/debt/](../debt/README.md)).
- **Фаза закрывается** по протоколу [workflow.md](../workflow.md) («Протокол завершения фазы»): зелёный `check`, dmg-reviewer без `error`, записанные решения и подтверждение Нурболата.

## 10. Расход токенов: экономно, но не жадно

Работа большая, а лимит недельный, поэтому каждое действие должно окупаться. Но качество эталона и платформы дороже сэкономленных токенов.

- **Одна фаза — одна сессия.** На контрольной точке состояние уже в `plan.md`, брифе и git. Дальше Нурболат открывает новую сессию, не `/compact`, и она стартует по протоколу «Старт». Две маленькие фазы допустимо сделать в одной сессии.
- **Внутри фазы — сжатие между шагами.** После каждого шага (отчёт агента принят, гейт зелёный, результат записан в `plan.md`) оркестратор делает `/compact` с фокусом на текущий бриф и ближайший шаг. Сессия не должна разрастаться до автосжатия: поздний `/compact` теряет детали, ранний дёшев. Порог автосжатия снижен до 50% (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` в `.claude/settings.json`).
- **Субагент живёт один шаг.** Каждый шаг — новый вызов `Agent`, продолжение через `SendMessage` только для доработки по замечаниям того же шага. Состояние между шагами передаётся через бриф, `plan.md` и git, не через контекст агента.
- **Оркестратор не читает код.** Агент получает путь к брифу. Ревьюер смотрит только diff. Вывод `check` фильтруется до итогов. Отчёты агентов короткие.
- **Reviewer запускается один раз на фазу**, по коду и гайду вместе. Повторно — только после правок по `error`.
- **Модель по умолчанию задана в ролях** (`.agents-core/roles/*.md`, поле `model`): `dmg-domain-author` — Opus, остальные — Sonnet. `dmg-tech-lead` переведён на Sonnet по итогу пилота: на Opus выходило в 2–5 раз дороже, а находок больше не было (Нурболат, 2026-11-04, `stream-dmg` Ф4). Параметр `model` в `Agent` переопределяет её для вызова:
  - **Sonnet** — машинная работа по готовому образцу: перенос по гайду и эталону, второй и следующие UC/ER по эталонному, переименования и правка потребителей, ревью среза по гайду с чеклистом ID.
  - **Opus** — работа, где образца нет или ошибка дорого стоит: первое воплощение вида артефакта (эталонные фазы `golden-wish`), правки `dmg-core`, ревью эталона и платформы, разбор эскалаций.
  - **DeepSeek flash** — по просьбе Нурболата: механические шаги и доработки вместо Sonnet, в ~12 раз дешевле на исполнителях, качество на шаг ниже. Распределение по шагам — [deepseek.md](./deepseek.md) §2.
  - Если Sonnet дважды подряд падает на гейте по одной причине, тот же шаг перезапускается на Opus. Только если и это не помогло — вопрос Нурболату.
- **Стратегические вопросы, которые не блокируют работу**, копятся в брифе («Открытые вопросы») и задаются пачкой на контрольной точке.

# Моделирование домена

**Назначение:** куда помещать доменную логику, как модули делят знание, как ошибки и данные пересекают границу модуля. Перенесено и переработано из бывшего `domain-boundaries.md`.

---

## 1. Модуль-владелец

1. **Определи владельца.** Чьи данные нужны правилу — там и живёт логика.
2. **Выбери объект** — ближе к данным, которыми оперирует правило:

| Логика | Объект |
|---|---|
| Инвариант, переход, вопрос в пределах одного агрегата | Ar |
| Право на действие (роль, владение, контекст) | Policy |
| Мутация нескольких агрегатов или решение не одного Ar | DCS |
| Вычисление на чтение поверх нескольких агрегатов | DQS |
| Нужны данные/решение другого модуля | делегирование в его Ar/Policy/DQS (по `dependsOn`) |

3. **Делегируй минимумом.** Зависимый модуль передаёт владельцу только нужное (идентификаторы, примитивы, его же агрегаты).
4. **Не дублируй.** Если CoursePolicy уже знает порядок модулей курса — StreamPolicy не пишет то же самое.
5. **Называй доменно.** Метод отвечает на доменный вопрос (`canEnrollNextModule`, `isPassed`), а не описывает структуру данных (`hasModule`, `isFirst`, сравнение `status === 'advanced'` снаружи Ar).

## 2. Антипаттерны

- ❌ Доменное решение в UC, ER, Job, Story (if по статусам, вычисления, выбор текста по состоянию).
- ❌ Чтение полей entity вне Ar и рендереров.
- ❌ Policy, которая разбирает структуру данных чужого модуля.
- ❌ `process.env` / глобальный `config` в домене и UI-компонентах — данные школы через `resolve.school`.
- ❌ Маскировка рассогласования данных пустым массивом или `undefined` — это баг, `throw`.
- ❌ Скрытые межмодульные мутации из UC (снять роль, уведомить) — это событие и ER в модуле-владельце.

## 3. Кейс: гейтинг модулей курса

*Задача:* студент записывается на модуль N, только если прошёл модуль N−1; первый модуль — без условий.

- ❌ *Всё в StreamPolicy:* stream знает `course.phases`, порядок модулей — знание курса утекло в stream.
- ❌ *Технические методы в CoursePolicy* (`hasModule`, `isEntryModule`): имена описывают данные, а не решение.
- ✅ *Итог:* `CoursePolicy.canEnrollNextModule(course, targetModuleId, completedModuleIds)` принимает решение о допуске. StreamPolicy извлекает `completedModuleIds` из **своих** агрегатов через `studentAr.isPassed()` и делегирует. UC stream вызывает только свою политику.

## 4. Границы модулей

**Данные.** Другой модуль получает агрегаты через фасад как `ReadonlyAr` и пользуется их API (`(await users.getUser(id))?.isAdmin()`). Мутировать чужой агрегат нельзя — только его UC/фасадом владельца.

**Ошибки.** Фасад возвращает `Result` с ошибками, объявленными в его контракте (`defineFacade`). Вызывающий UC может:
- **пробросить** ошибку зависимости — сослаться на неё в своём `errors` (без переименования; коды уникальны в приложении);
- **перевести** в свою — только если смысл меняется. Пример: `USER_NOT_FOUND` при поиске наставника → `MENTOR_NOT_ASSIGNED` в stream.

Пробросить можно только то, что объявлено в контракте фасада: внутренние ошибки чужого модуля, не вынесенные в фасад, наружу не видны. Исход «сущности нет» (`COURSE_NOT_FOUND`) — штатный для фасада: он объявляется в контракте, и зависимый модуль пробрасывает его как есть, а не подменяет своей ошибкой.

**Поведение.** Нижестоящий модуль не вызывает вышестоящий. Нужна реакция «наверху» — публикуется событие, вышестоящий подписывается ER.

## 5. Агрегат

- Создание и восстановление разделены: `Ar.create(input, at): Result<Ar>` (бизнес, событие; базовые поля — `newEntity(uuid, at)`) и `Ar.restore(snapshot)` (доверенно, без событий).
- Время — аргумент операции (`complete(at)`), часы домен не читает (D-34). Статус меняется только через `transition` по правилам Def (D-35); версию ведёт база (D-36).
- Мутация: проверка → черновик → валидация инвариантов → фиксация. Повреждённое состояние в памяти невозможно.
- Вопросы к состоянию — методами, а не геттером на каждое поле; идентификаторы (`uuid`, связи) — геттерами.
- VO не имеют `createdAt`/`updatedAt` и идентичности.

# Новые роли агентов — план внедрения

**Назначение:** какие роли добавляются к конвейеру [agents.md](./agents.md) §1, зачем, когда вызываются, как их обкатывают и по каким критериям переносят в пакет `dmg-core`. Нынешние роли (`domain-author`, `api-author`, `migrator`, `reviewer`) отвечают на «как сделать»; новые — на «зачем», «что для бизнеса», «как по архитектуре» и на узкие риски.

---

## 1. Ключевые правила

1. **Сначала проект, потом пакет.** Новая роль рождается в `.agents-core/roles/` u7-school, проходит пилот на реальных треках и только по критериям §5 переезжает каркасом в `dmg-core/agents/roles/`; проектная часть остаётся в `.agents-core/` (как общий блок сейчас).
2. **Одна роль — один вопрос.** Роль не дублирует `reviewer` и соседей; пересечение — повод слить роли или сузить промпт.
3. **Только чтение и отчёт** (`read`, `grep`, `find`), кроме тестировщика (пишет тесты). Отчёт — в бриф среза или spec трека, не в чат.
4. **Вызов по триггеру**, а не на каждый шаг (§3). Модель — Sonnet ([agents.md](./agents.md) §10); Opus — только если роль на Sonnet дважды не справилась.
5. **Роль не знает лишнего.** Знания задаются явно (столбец «Знает» §2): пользователь не видит архитектуры, продакт не видит устройства `dmg-core`.

## 2. Состав

| Роль | Вопрос | Знает | Выход | Каркас |
|---|---|---|---|---|
| **user** (персона) | ценно / не ценно, удобно / не удобно | персону (любопытный, студент, автор, ментор…) и возможности UI: сейчас `runners/u7-bot/src/controllers/*/ui-spec.md` и stories, позже манифесты UI ([ui-manifests.md](./ui-manifests.md)) | отчёт по сценариям персоны | пакет (каркас) + проект (персоны `.agents-core/personas/<name>.md`) |

| **architect** | как реализовать: модули, Def, события, `dependsOn`, затронутые ID `rules.md`, разбиение на срезы | `dmg-core` изнутри, `rules.md`, эталон `wish` | черновик брифа среза | пакет |
| **test-designer** | какие сценарии и границы; red до реализации | Def среза, гайд тестирования пакета, сохраняемое поведение (для переноса — характеризация) | падающие тесты + список сценариев в брифе | пакет |
| **data-keeper** | что станет с уже лежащими записями | формат `state`/снимков, репозитории, `docs/backup.md`, правило данных `AGENTS.md` | отчёт: совместимость чтения, путь миграции, нужен ли бэкап | пакет (общее: старый формат записей) + проект (`data/`) |
| **access-auditor** | кто может вызвать, нет ли обхода, не утекают ли чужие данные | Policy, `Caller`, DQS/`view`, ER и Job как обходные пути | отчёт с ID правил | пакет |
| **documentarian** | документы пакета и проекта сходятся с кодом | гайды, `llms.txt`, `decisions.md`, `migration.md` §6 | список расхождений | пакет |
| **methodist** | контент курса по правилам обучения | `conductor/guides/lesson-design.md` | отчёт по уроку / mentor-файлам | проект |

## 3. Место в процессе

- **Постановка** (`conductor-newtrack`): `user` → `product` → `architect`. Отчёты — в spec и брифы. Для чистого переноса модуля (поведение не меняется) `user` и `product` не вызываются.
- **Реализация** (`conductor-implement`, срез [agents.md](./agents.md) §3): `test-designer` (red) → автор (green) → гейт → `reviewer`.
- **Условные проверки после гейта** — по путям в diff: `state`, `*.repo.ts`, снимки → `data-keeper`; Policy, `Caller`, DQS → `access-auditor`. Триггер со временем проверяет `scripts/agent-gate.ts`.
- **После фазы** — `documentarian`, если фаза меняла документы пакета или гайды.

## 5. Критерии годности

Пилот роли ведётся в `summary.md` трека, раздел «Пилот ролей»: на каждый вызов — повлиял ли отчёт на решение, сколько замечаний принято, правился ли промпт. Роль **годна**, когда за два трека:

1. **Польза:** хотя бы в половине вызовов отчёт изменил spec, бриф, тесты или код — нашёл то, что иначе пропустили бы.
2. **Сигнал, а не шум:** принято не меньше двух третей замечаний; оркестратор не переписывает отчёт заново.
3. **Нет дублей:** замечания почти не пересекаются с `reviewer` и другими ролями.
4. **Окупается:** работает на Sonnet, отчёт короткий; расход роли меньше, чем стоила бы пропущенная ошибка (оценка оркестратора в разделе пилота).
5. **Стабильна:** последний трек пилота прошёл без правки промпта.

Для **переноса в пакет** дополнительно:

6. **Обобщается:** в промпте нет специфики u7-school — она вынесена в параметры (персона) или общий блок проекта; роль даёт осмысленный отчёт на учебном модуле `dmg-core`.

Не годна после двух треков — роль удаляется или сливается с соседней; решение фиксируется `TR-<n>` ([debt.md](./debt.md) §6). Перенос в пакет и смена формата ролей — стратегические (форма API `dmg-core`, [agents.md](./agents.md) §9): только с Нурболатом.

# State — гайд

**Назначение:** схема entity агрегата, то есть единственное место структуры его состояния: `packages/domain/src/<m>/<a>/<a>.state.ts`.

> Эталон — модуль `wish`. Базовые поля и даты переходят на `BaseEntityFields` и `F.timestamp` в Фазе 2 (DEBT-24). До того смотри на форму базовых полей в [task.state.ts](../../../packages/dmg-core/src/testing/example/todo/task/task.state.ts).

---

## 1. Когда применять

- Описываешь, из чего состоит агрегат: поля, статус, value object (VO).
- VO, который нужен только этому агрегату (у `wish` это `WishTarget`), лежит в том же файле. Общий для модуля VO выносится в `shared/` ([manifests.md](../manifests.md) §3).
- Правила переходов и запреты сюда не пишутся. Им место в Ar и Policy (гайды «aggregate» и «policy»).
- Для вывода UC схему не копируй: DTO выводится из state через `v.pick`/`v.omit` (DOM-11).

## 2. Команда

`bun run gen aggregate <m>.<a> --write` создаёт `<a>.state.ts` вместе с остальными артефактами агрегата. TODO в шаблоне — поля и статусы. Если у legacy-модуля нет `<m>.module.ts`, генератор не запустится: файл создаётся вручную по `stateSrc` из [aggregate.ts](../../../scripts/gen/kinds/aggregate.ts), так сделано в эталоне.

## 3. Эталон

- [wish.state.ts](../../../packages/domain/src/wish/wish/wish.state.ts): `WishState`, `WishTarget` и `WishStatus` — у каждого одно имя и для схемы, и для типа; `target` — `v.variant` по `kind` с описанием на каждой ветке.
- [wish.state.test.ts](../../../packages/domain/src/wish/wish/wish.state.test.ts): проверки «принимает/отклоняет» и проверка, что описание есть у каждого поля.
- [state.ts](../../../packages/domain/src/wish/state.ts): подпуть `@u7-scl/domain/<m>/state`, только для рендереров UI.

## 4. Чеклист правил

- DOM-11 — базовые поля задаются только через `...BaseEntityFields`, остальные идентификаторы — через `F.uuid('<кого>')`; свои `v.uuid()` запрещены.
- DOM-12 — даты задаются через `F.timestamp`, `v.isoDateTime` не используется.
- MAN-02 — у каждого поля, у ветки `variant` и у `kind` есть `description` (через `F.*` или `v.description`).
- DOM-01 — state импортируют только Ar своего агрегата и UI. Остальным нужен доменный API.
- CODE-01 — файл `<a>.state.ts`, схема `<A>State`, VO — `<A><Vo>`. Суффикс `Schema` не ставится.

## 5. Типичные ловушки

- **Чужая схема ради `uuid`.** `CourseSchema.entries.uuid` тянет зависимость от state другого модуля. Правильно: `F.uuid('курса')`.
- **Тексты ошибок в схеме.** Пользователь видит ошибки команды UC, а не ошибки state, поэтому свои тексты здесь не нужны.
- **Сырые данные через экспортированную схему.** Репозиторий разбирает `<A>ArDef.state`. Только в нём срабатывает фолбэк `updatedAt = createdAt` для legacy-записей (D-36). Если разобрать данные через `<A>State`, legacy-записи без `updatedAt` не пройдут схему.
- **Генератор на legacy-модуле.** `gen aggregate --adopt` требует паспорт модуля, а `gen module` сразу создаёт заготовки всех артефактов. Если модуль переводится по фазам, state пишется вручную.

## 6. Как тестировать

Для каждого VO и статуса: допустимое значение принимается, недопустимое отклоняется (`v.safeParse`). Отдельный тест проверяет, что описание есть у каждого поля. Тесты не длиннее 20 строк ([testing.md](../testing.md), TST-04). Логика переходов тестируется в Ar, а не в state.

# Стратегия документации

**Назначение:** какая документация бывает, для кого, где лежит и как не устаревает. Общая картина — [vision.md](./vision.md) §5, решение — D-81.

---

## 1. Два вида

| | Доменная | Техническая |
|---|---|---|
| **Для кого** | PO, аналитик, LLM | агенты, программисты |
| **Что** | модули, агрегаты, статусы, UC, события, ошибки, права, каскады | архитектура, правила, процессы, решения |
| **Источник** | граф манифестов | вручную + генерация из кода |
| **Обязательность** | обязательна, под неё строится архитектура | ручная часть — обязательна, генерация — по возможности |

## 2. Доменная документация

- Генерируется из графа: `bun run docs:domain` → `docs/domain/` (Markdown + Mermaid) и `docs/domain/graph.json`.
- Структура повторяет граф: `index.md` (L0, карта модулей) → `<module>/index.md` (L1) → `<module>/<aggregate>.md` (L2); каталоги `events.md`, `errors.md`, `use-cases.md`.
- **Коммитится в git.** Diff в PR показывает изменение домена — это ревью для PO. CI проверяет актуальность (`docs:domain --check`).
- `graph.json` — граф системы (D-78): кроме домена, в него войдут узлы UI, развёртывания и систем. Он питает сайт, просмотрщик и MCP resources — без отдельного источника.
- **Запросы агента** — CLI поверх `graph.json`: `ls`, `show <id>`, `impact <id>`, `who-calls <id>`. Устройство приложения агент узнаёт запросом, в код идёт за реализацией.
- Качество зависит от `label`/`description` в Def и описаний полей (MAN-01, MAN-02).
- UI-часть (после трека ui-manifests): превью экранов, карта переходов, матрица «роль × экран» — [ui-manifests.md](./ui-manifests.md) §3.

## 3. Описания манифестов для LLM

**Цель:** дешёвая общая картина приложения для LLM (и людей): быстро поднять контекст, за деталями — в код. Описывает смысл, а не реализацию.

- Рядом с каждым Def — `<имя>.md` (`add-user.uc.md`). Две части:
  - **факты** — вход, выход, ошибки, события, `callers`, связи; генерируются скриптом из Def, без модели;
  - **смысл** — зачем, типичные сценарии, тонкости, пример; пишет LLM.
- Frontmatter: `defHash` (хеш **нормализованного** Def — `normalize(def)` из core), модель, дата обновления.
- Конвейер `bun run docs:llm`, каждый шаг дешевле следующего:
  1. скрипт сравнивает `defHash` — нет изменений → конец; меняет только факты;
  2. структурный diff Def + текущий смысл → модель решений (вопрос-вероятность «смысл устарел?»): ниже порога → обновить `defHash`; серая зона — как «да»;
  3. да → сильная модель переписывает смысл, обновляются `defHash` и мета.
- Модель решений — порт (выбор, оценка, вероятность), реализация — Jev (TypeSafe AI). Текст не пишет и даёт только сигнал: в `--check` не участвует. Ещё применения — оценка качества `description`, маршрутизация вопроса в agent-ui.
- Пишущие модели вызываются через CLI агентов в headless-режиме (`claude -p`, pi print-режим) — подписки, без SDK и API-ключей.
- `.md` руками не правятся (артефакт для LLM); правка допустима, скрипт передаёт текст модели как основу.
- **Проверка:** `docs:llm --check` — детерминированно, без модели. В `bun run check` — `warn` со списком устаревших; **в гейте релиза — блокирует**.
- **Сборка:** индекс по соглашению `llms.txt`: уровень приложения (техническая стратегия — [index.md](./index.md), доменная — карта модулей L0 со смыслом), дальше модули. Дерево строится детерминированно из графа; каскадных хешей нет. Тот же индекс — MCP resources (D-18); `docs/domain/` собирается из фактов графа и смысловой части этих `.md`.

## 4. Техническая документация

**Ручная** — `conductor/architecture/` (этот каталог): решения, слои, правила, процессы. Принципы:
- описывает то, чего нельзя вывести из кода: *почему*, границы, правила;
- не дублирует сгенерированное и код — ссылается на эталон и файлы;
- файлы 30–100 строк, по правилам скилла `conductor-docs`.

**Генерируемая** — `bun run docs:tech` → `docs/tech/`, коммитится:
- граф пакетов и модулей (`dependsOn`, фасады);
- статус каталога правил: какие ID проверяются машинно и где реализация проверки;
- wiring модулей: Def → реализация.

## 5. Где что лежит

| Что | Где |
|---|---|
| Продукт, треки, планы | `conductor/` (product, tracks, roadmap) |
| Архитектура и правила | `conductor/architecture/` |
| UI-гайды бота | `conductor/architecture/ui/` |
| Процедуры (бэкап и т.п.) | `docs/*.md` |
| Сгенерированная доменная | `docs/domain/` |
| Описания Def для LLM | `<имя>.md` рядом с Def, индекс `llms.txt` |
| Сгенерированная техническая | `docs/tech/` |

## 6. Комментарии в коде

- Def несут документацию в `label`/`description` — JSDoc их не дублирует.
- Комментарий объясняет *почему*, а не *что*. На русском.
- Что допустимо в комментарии и предел JSDoc — CODE-04 пакета (`node_modules/dmg-core/docs/reference/rules.md`, решение D-59 пакета); действует и в u7-school. Маркеры `C-DEBT-<n>` — по [conductor/debt/](../debt/README.md).

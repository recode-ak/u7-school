# Манифесты UI

**Назначение:** концепция манифестов UI-слоя — тот же принцип DMG, что в домене: декларация рядом с кодом, граф, генерируемая документация. Общая картина и последовательность — [vision.md](./vision.md); решения — D-26, D-79, D-80. Реализация — пакет `dmg-ui` (отдельный репо рядом с `dmg-core`), эталон — один контроллер бота; до него UI живёт по [ui/](./ui/bot-architecture.md).

> Статус: **концепция.** Детали API фиксируются на эталонном UI-срезе.

---

## 1. Матрёшка

| Уровень | Def | Декларирует | Сейчас в боте |
|---|---|---|---|
| приложение | `defineUiApp` | платформа (bot / web / mobile), состав UI-модулей, меню | `BotUiApp` |
| UI-модуль | `defineUiModule` | цель пользователя, роли, `load: () => import(...)` — ленивая загрузка | `Controller` |
| сторис | `defineStory` | цель, `callers`, **ссылки на Def UC**, слушаемые события | `Story` |
| экран | `defineScreen` | содержимое, действия (кнопки) и их переходы, примеры состояний | `Screen` / `DialogResponse` |

- **Манифест статичен, код ленив:** граф и документация строятся без загрузки реализаций.
- **UI-модуль ≠ доменный модуль.** UI режется по целям и ролям (learning, mentor, school); связь с доменом — только через ссылки на UC.
- **Сторис общая, экраны — по платформам.** Логика сценария одна; бот и web объявляют свои экраны к ней.
- **Карточка** — представление схемы домена (выход UC или `view()` агрегата), а не часть сторис: её переиспользуют ручные экраны и автогенерируемый UI. У карточки свой манифест (`defineCard`: схема, примеры, рендереры по платформам); экран с одноразовым представлением обходится своим рендером (D-80).
- **Матрёшка — только для ручных сторис** (bot-ui, web-ui). cli-ui генерируется из графа, agent-ui — транспорт; [vision.md](./vision.md) §3.

## 2. Ключевые правила

1. UI обращается к бэку **только через Def UC** (команда `ucDef.command(input)`, D-49: в процессе — `appApi.dispatch(moduleDef, …)`, для удалённого UI — `ModuleApi` с HTTP-транспортом). Отдельного «apiFacade»-манифеста нет — он был бы дублем.
2. Сторис вызывает только UC из своего списка (рантайм-ассерт в test/dev, как `emits`).
3. `callers` сторис ⊆ `callers` каждого её UC: сторис для `guest` не вызывает UC «только для `user`» (контрактный тест; см. [caller.md](../../node_modules/dmg-core/docs/reference/caller.md)).
4. Каждое действие экрана объявляет, куда ведёт: другой экран, сторис или UC. Незаявленный переход — ошибка в test/dev.
5. Экран объявляет **примеры** — именованные состояния на фикстурах (`empty`, `withProgress`, `noAccess`…).

## 3. Спецификация экранов живёт в манифесте

Ручные `ui-spec.md` у контроллеров отстают от кода. Их заменяет то, что выводится из `defineScreen`:

- **превью экрана** — генератор документации рендерит каждый пример **настоящим** рендерером (текст и кнопки, как увидит пользователь). Расхождение с кодом невозможно: превью и есть вывод кода;
- **карта переходов** — из действий экранов: экран → кнопка → экран/UC (диаграмма в доменной документации);
- **кто видит** — из `callers` и ролей: матрица «роль × экран».

Примеры экрана одновременно служат snapshot-тестами: изменение вывода видно в diff.

**Уведомления.** Сторис объявляет `on: Событие` и экран с примером; текст в манифест не пишется. Граф показывает у события, кто получает (роль) и что видит (превью).

Статусы «✅ реализовано / ❌ / 📋 в бэклоге» в манифест **не** входят: запланированное описывается в spec трека, в манифест попадает с кодом.

## 4. Граф UI

Узлы: приложение → UI-модули → сторис → экраны. Связи: переходы экранов, сторис → UC, сторис ← события. Это не отдельный граф, а узлы общего графа системы (D-78); сшиваются с доменными по ссылкам на Def UC, что даёт:
- какие экраны затронет изменение UC;
- UC без UI; экраны, недостижимые из меню;
- проверку согласованности `callers`.

# Решения проекта (ADR-список)

**Назначение:** реестр решений проекта u7-school: процесс, документация, переход, UI. Решения платформы DMG (D-01…D-18, D-25, D-28, D-32…D-40, D-42…D-60, D-62, D-66…D-74, D-84) — в пакете: [decisions.md](../../node_modules/dmg-core/docs/decisions.md). Нумерация общая: новое решение берёт следующий свободный номер, платформенное добавляется в пакет, проектное — сюда; старое помечается «заменено D-NN».

---

**D-19. Доменная документация генерируется и коммитится.** Техническая — вручную в `conductor/architecture/` + генерируемый справочник. См. [docs-strategy.md](./docs-strategy.md).

**D-20. Стандарт задаётся генераторами и проверками.** Скаффолдинг (`bun run gen …`) создаёт структуру; каталог [rules.md](./rules.md) с ID — источник проверок; каждая машинная проверка ссылается на ID.

**D-21. Мультиагентный процесс на conductor.** Оркестратор + domain-author, api-author, migrator, reviewer. Conductor остаётся памятью проекта, `conductor-implement` получает режим оркестратора. См. [agents.md](./agents.md).

**D-22. Поэтапный переход (strangler).** Старое и новое сосуществуют; перенос и перепроектирование — разные треки. Ход перехода — `summary.md` трека `legacy-removal` в `conductor/archive/`; завершён 2026-11-12.

**D-23. Одно место для технической документации.** Всё техническое — в `conductor/architecture/` (уточнено D-30: документация платформы DMG — в пакете `dmg-core`, `node_modules/dmg-core/docs/`). Старые `code_styleguides/`, ddd-скиллы и `arch-boundary-design` удалены; паттерны немигрированного кода жили в отдельном документе (удалён с завершением перехода, трек `legacy-removal`).

**D-24. Две агентные среды: Claude Code и pi.** Основная — Claude Code. pi — внешний исполнитель, которого Нурболат включает сам (лимиты, экономия); Claude Code им не управляет. Общая память и точка передачи — conductor и git. Тексты ролей и скиллы — одни на обе среды. См. [agents.md](./agents.md) §8.

**D-26. Манифесты UI.** Матрёшка `defineUiApp` → `defineUiModule` (ленивая загрузка) → `defineStory` → `defineScreen`. UI вызывает бэк только по ссылкам на Def UC, отдельного apiFacade нет (уточнено D-49: Def собирает команду `ucDef.command(input)`, вызов — `apiApp.dispatch(moduleDef, …)` в процессе, `ModuleApi` для удалённого UI). Спецификация экранов (превью из примеров настоящим рендерером, карта переходов, кто видит) генерируется из манифестов и заменяет ручные `ui-spec.md`. Реализация — после golden-wish. См. [ui-manifests.md](./ui-manifests.md).

**D-27. Описания манифестов для LLM.** Рядом с каждым Def — `<имя>.md`: факты генерируются из Def, смысл пишет LLM. Актуальность — по хешу нормализованного Def: скрипт → дешёвая модель («пересматривать ли») → сильная модель. В `check` — `warn`, в гейте релиза — блокирует. См. [docs-strategy.md](./docs-strategy.md) §3.

**D-29. Платформа DMG — внешний пакет `dmg-core`.** Выносится только DMG (не legacy `@u7-scl/core`); мосты к legacy живут в монорепо и зависят от `dmg-core`, не наоборот. Ставится из npm по semver. Внутренний алиас — `#core/*`; legacy-алиасы переименованы в `#<слой>-legacy/*`, чтобы освободить имена. Legacy-алиасы удалены вместе с legacy (трек `legacy-removal`).

**D-30. Пакет несёт документацию и агентные инструменты.** `dmg-core` поставляет `docs/`, `llms.txt`, скилы и роли агентов; `dmg-core init`/`sync --check` доставляют их в проект потребителя. Генераторы артефактов (`dmg-core gen`) — тоже в пакете, раскладку задаёт секция `gen` `dmg-core.json` проекта, `ArchApp.layout` строится из неё же (`GenLayout`, 2026-10-27). Документация платформы существует в одном месте — в пакете; проект ссылается на неё. Критерий: свежий проект на `dmg-core` может работать без доступа к u7-school. См. трек `dmg-core-extract`, Фаза 5.

**D-31. Платформа DMG — пакет `dmg-core`.** Сначала жила подпутём `@u7-scl/core/dmg` рядом с legacy (strangler); в треке dmg-core-extract вынесена в workspace-пакет `platform/dmg-core` (с D-61 — отдельный репо `~/dev/tools/dmg/dmg-core`) (импорт `dmg-core`, `dmg-core/testing`, алиас внутри — `#core/*`). Legacy-алиасы получили суффикс `-legacy`.

**D-61. Подключение вынесенного `dmg-core` в u7-school.** (Бывший D-55: номер совпал с решением пакета.) Репо пакета — `~/dev/tools/dmg/dmg-core` (рядом позже — `dmg-ui` и другие пакеты DMG). До релиза (пушей нет) — `"dmg-core": "file:<относительный путь>"` во всех `package.json`, где пакет объявлен: bun (hoisted-линкер u7-school) кладёт в `node_modules/dmg-core` каталоги с символьными ссылками на файлы репо пакета — правки видны сразу, новые файлы — после `bun install`; вместе с ними копируется `node_modules` пакета, поэтому у пакета своя копия peer `valibot` (следить, чтобы версия совпадала с проектной; при установке из git её нет); правка платформы — в репо пакета, затем `bun install` в u7-school. При релизе — `git+ssh://git@github.com/<owner>/dmg-core.git#v<версия>` (тег; коммит фиксирует `bun.lock`), на прод-сервер — deploy key. Отвергнуты: `link:` (глобальная регистрация, только на одной машине), workspace вне корня (пакет фактически остаётся в монорепо), tarball в репо (двоичные файлы по версиям), npm/GitHub Packages (scope и токены; можно позже). Уточняет D-29 («из npm по semver»). Нурболат, 2026-10-28, трек `dmg-core-standalone`. **Исполнено 2026-11-14** (релиз v0.3.0): `recode-ak/dmg-core`, тег `v0.1.1`.

**D-41. Межмодульный побочный эффект — выбор места по каждому случаю, решение Нурболата.** Каждое место, где UC/ER/Job через фасад меняет состояние чужого модуля (запись, запуск процесса, отправка), разбирается отдельно: варианты, сценарии сбоя каждого, рекомендация — и выбор Нурболата явно, по этому месту (не тактическое решение, не «по образцу»). Типовые варианты: (1) вызов фасада в `execute` после `uow.register`, до фиксации — для эффекта, без которого команда не выполнена; сбой фасада — ошибка UC, ничего не записано; риск — эффект без записи при сбое фиксации; (2) событие своего модуля → ER, вызывающая фасад после фиксации — для реакции на факт; риск — запись без эффекта, если ER упала; (3) хук после фиксации в UoW — API платформы, пока нет. Выбор и принятый риск записываются в бриф среза с условием пересмотра; оставшийся временный код — записью `C-DEBT-<n>` ([debt](../debt/README.md)).

Первый случай — `create-course-wish` (`questionnaireFacade.startStandard`): вариант 1, Нурболат, трек `golden-wish` (Ф8); эффект без записи возможен при сбое фиксации и при `OUTPUT_VALIDATION` (баг реализации). Пересмотреть при внешней шине или outbox.

**D-63. Доменные события не несут адрес доставки и представление.** Payload Def-события — идентификаторы и доменные факты; `telegramId`, снимки ответа (`response`) и тексты в событие не кладутся. Story-подписчик получает адрес через `GetTelegramAddressesUcDef` модуля `user` (UC доступен только `system`), экран строит по query-UC своего модуля. Так Job и ER остаются доменными (не зависят от канала доставки), а событие не устаревает при смене способа показа. Первое применение — `questionnaire`. Исключение: `wish.invited` несёт `telegramId` адресата — ER резолвит его из профиля, по нему UI шлёт карточку (осознанно, ревизия v0.3.0). Нурболат, 2026-11-04, трек `questionnaire-dmg`.

**D-64. Этап курса — метка в программе, а не контейнер модулей.** Программа курса — плоский `moduleIds: string[]`; этапы — необязательный список `phases: [{ title, track?, fromModuleId }]`: этап отмечает модуль, с которого начинается. Пустой список — курс без этапов, бот рисует плоский список модулей. Инварианты Ar: каждый `fromModuleId` есть в программе, метки идут в порядке программы, первый этап (если есть) начинается с первого модуля. Этап модуля (место модуля, навигация) вычисляется по меткам; наружу `get-course` отдаёт вычисленные `stages: [{ title, track?, moduleIds }]` — клиенты метки не разбирают. Так модуль можно вставить, убрать или переставить, не перекладывая его между контейнерами, а курс без этапов не требует фиктивного этапа. Формат `data/courses/courses.json` переводится в треке (`phases[].moduleIds` → `moduleIds` + `phases[].fromModuleId`), чтение строгое. Нурболат, 2026-11-05, трек `course-dmg`.

**D-65. Клиент спрашивает — модуль-владелец разруливает.** Клиент не сравнивает идентификаторы чужого модуля между собой и не выводит из них доменные факты, а задаёт вопрос модулю-владельцу через его UC и получает вердикт. Первое применение — `course`: пререквизит модуля — `getModulePrerequisite({ moduleId, passedModuleIds })` → `{ admitted: true }` / `{ admitted: false, reason: 'previous-not-passed', title }` / `{ admitted: false, reason: 'closed' }`; `stream` передаёт id модулей пройденных потоков, `StreamAr.teachesModule` и сравнение в `student.rules.ts` уходят. Контракты для `wish` (`GetSameModules`, enrollment, «курсы, включающие модуль / начинающиеся с модуля») уже вопросы и не меняются. Учёт истории модулей (замена модуля новым id) — внутреннее дело `course` ([course-module-history.md](../roadmap/course-module-history.md)); пока реализация — равенство id. Нурболат, 2026-11-05, трек `course-dmg`.

**D-75. Отказ перехода жизненного цикла — `kind: 'conflict'`, невалидный вход — `validation`.** Вход валиден, но операция несовместима с текущим статусом агрегата — семантика 409; так во всех модулях (27 ошибок переходов на ревизии v0.3.0). Клиенты по HTTP-коду не ветвятся: бот различает отказы по `code`. Трек `golden-wish`, ревизия `revision-release`.

**D-76. Id апдейта Telegram до story — `AsyncLocalStorage`, а не поле сессии или экземпляра.** `BotRequestContext` (`platform/core/src/ui/bot/bot-request-context.ts`) ставит транспорт при постановке апдейта в очередь чата, читает `dispatchUc` (`requestId = tg:<update_id>#<n>`); реакции UI на события — `UiEventContext` со следом из конверта. Поле сессии сохранялось бы в JSON на каждом апдейте, поле экземпляра story даёт гонку между чатами. Вне апдейта контекста нет — `warn` (ERR-07). Явная передача id в контракте story — C-DEBT-41 (`dmg-ui`). Трек `dmg-cleanup`, ревизия `revision-release`.

**D-77. Повтор `stream.created` снова приглашает желающих — как в v0.2.6.** В state желания не хранится, в какие потоки уже приглашали: повтор доставки отсекает `Inbox` (D-47 пакета), повтор самого события редок. Список приглашённых потоков в state (схема, Def, миграция `wishes.json`) — при реальной жалобе на дубли. Само приглашение пишется через `WishAr.invite` (`version` и `updatedAt` растут на каждое приглашение); при `VERSION_CONFLICT` на N-м желании приглашения до него уходят, после — нет (D-15). Нурболат, 2026-11-12 (ревизия v0.3.0).

**D-78. Один граф системы.** Домен, UI, развёртывание и системы поставляют узлы (`kind`, `id`, `label`, `description`, родитель) и рёбра в общий граф; своих графов слои не строят. Ядро графа — `dmg-core/graph`, виды узлов добавляют пакеты слоёв; `id` узлов иерархические. Один `graph.json` питает документацию, запросы агентов и просмотрщик. *Почему:* ценность — в сшивке слоёв (экран → UC → событие → уведомление); отдельные графы её не дают. Платформенная часть при реализации записывается решением пакета. Нурболат, 2026-11-14. См. [vision.md](./vision.md) §2.

**D-79. Три механизма UI; `dmg-ui` — отдельный пакет.** Уточняет D-26. (1) bot-ui и web-ui — ручные сторис: манифест сторис общий, экраны и рендер по платформам; web заранее не проектируется, эталон — бот. (2) cli-ui — генерируется из графа: форма по схеме входа UC, карточка по схеме выхода (`dmg-cli`, wizard бота). (3) bot-agent-ui — агент над MCP из манифестов (D-18) с `Caller` спросившего: Policy вызывается всегда. `dmg-ui` — пакет рядом с `dmg-core` (`~/dev/tools/dmg/`), не подпуть (D-33). Агент исполняет query сразу, команды — только после подтверждения пользователя: несколько команд — один явный перечень и одно подтверждение, отдельное на каждую — когда этого требует логика. Нурболат, 2026-11-14. См. [vision.md](./vision.md) §3.

**D-80. Требование к UI — пример в манифесте.** Уточняет D-26. В манифесте — `label`, короткое `description`, структура и именованные примеры состояний; превью рендерит настоящий рендерер, оно же snapshot-тест. Длинный смысл — в соседнем `.md` (D-27). Тексты уведомлений не пишутся в манифест: сторис объявляет `on` события и экран с примером, граф показывает получателя и превью. Карточка — манифест представления схемы домена (примеры, рендереры по платформам), общий для ручных экранов и автогенерируемого UI; экран с одноразовым представлением обходится своим рендером. *Почему:* `ui-spec.md` лежит далеко от кода и расходится с ним; пример разойтись не может. Нурболат, 2026-11-14. См. [vision.md](./vision.md) §4.

**D-81. Документация продукта — из графа; модели только там, где нужен смысл.** Уточняет D-19 и D-27. Факты — детерминированно из `graph.json`; агенту — запросы к графу из CLI и MCP resources, человеку — `docs/domain/`, сайт и просмотрщик из того же файла. Дешёвые решения конвейера («пересматривать ли смысл», качество описаний, маршрутизация вопроса agent-ui) — через порт модели решений (выбор, оценка, вероятность); реализация — Jev (TypeSafe AI), SDK или HTTP — деталь адаптера. Ответ модели — только сигнал: калибровка статистическая, блокирующие проверки остаются детерминированными. Нурболат, 2026-11-14. См. [docs-strategy.md](./docs-strategy.md).

**D-82. Матрёшка приложений через модуль-владелец; масштабы задаёт пользователь платформы; развёртывание — манифест того же графа. Сейчас только задел.** Единица любого масштаба — приложение на DMG со своими модулями, агрегатами, UC, ER, Job, процессами и шиной. Модуль приложения может владеть дочерними приложениями: его операции обращаются к ним через типизированный фасад по опубликованному контракту, фасад выдаёт резолвер; транспорт (в процессе или удалённо) — деталь развёртывания, поэтому сборка возможна монолитом и распределённо. Изоляция на каждом уровне: внутренние события и фасады дочернего наружу не выходят. Внутренняя механика `dmg-core` при этом не меняется: для владельца сёстры — обычные модули, его ER слушает событие одного и вызывает UC другого; новое — только дочернее приложение у модуля и типизированный доступ к его API через Def UC. Сёстры общаются через приложение-владельца; зависимости — сверху вниз, обратное — событиями, взаимная связь — явным объявлением. Платформенное приложение не входит в состав и доступно с любого масштаба через резолвер. Названия и число масштабов — словарь проекта. Манифесты описывают типы, развёртывание — экземпляры (юниты, хранилища, транспорты, где и сколько раз запущено). Отвергнуты: контейнер без поведения и фиксированные уровни в платформе. Сейчас закладываются иерархические `id`, признак публичности UC и событий, контракт приложения, пригодный для фасада, и метка масштаба; остальное — при втором приложении. Нурболат, 2026-11-14. См. [vision.md](./vision.md) §7.

**D-83. Процесс — именованный путь по графу над модулями.** Манифест процесса ссылается на Def операций и событий любых модулей и ничего не исполняет: работу делают UC, ER и Job. Операция о процессе не знает — участие вычисляет граф (пометка процесса в Def операции отвергнута: модуль зависел бы от слоя над ним). Переходы между шагами выводятся из графа; объявляются только действия человека и ожидание времени. Валидность: ссылки — типизация; путь от начала до каждого исхода — проверка архитектуры; межмодульная цепочка вне процессов — предупреждение; смысл и границы — ревьюер. Платформенная часть при реализации записывается решением пакета. Нурболат, 2026-11-14. См. [vision.md](./vision.md) §6.

**D-85. Снимок потока хранит заголовки проектов и уроков; живая правка заголовка доходит до потоков явной синхронизацией.** Снимок контента — самодостаточная замороженная навигация: дерево id с заголовками проектов и уроков (`domain/src/course/content-snapshot.ts`), тексты шагов читаются по id из `course` (системный UC по `stepIds`). «Чистое дерево id» отвергнуто: каждый экран навигации потока и DQS прогресса (`student-progress.dqs.ts`) потребовали бы запрос заголовков в `course` (D-69 — лишняя зависимость ради редкой правки), архивные и неопубликованные заголовки — отдельного правила чтения, живые `streams.json` — миграции.
